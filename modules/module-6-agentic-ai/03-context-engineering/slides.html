The real cost lever: context

Class 6.2 (Orchestration) made the team coordinate. Every agent on it pays for every token it reads, so what each agent sees decides both the bill and the quality. Today we choose that context deliberately and measure the difference with the provider's own token counts.

Technique 1Each agent sees only what it needs

The team state can hold everything. Holding data and showing it to a model are separate decisions. A small per-agent context function picks the fields one agent needs and formats only those into its prompt.

The naive defaultPass the whole state to every node's prompt. It works at first and then gets slower, costlier, and less accurate as the state grows with every round.
The question to ask per agent"What would a human in this role need on their desk?" A copy editor needs the draft and the facts behind it, not the researcher's search history.

The shapeOne state, a different view for each agent

The state on the left grows with every step. Each context function is a filter between it and one agent's prompt.

In the buildwriter_messages() returns the question and the handoff notes. reviewer_messages() adds the draft. Neither sees raw transcripts or old drafts.

Where tokens goThe per-agent token budget

$$T_{agent} = T_{system} + T_{tools} + T_{context} + T_{task}$$

Every term\(T_{system}\): the instructions. \(T_{tools}\): the tool schemas, sent on every call. \(T_{context}\): what you choose to show from the state. \(T_{task}\): the request itself. The single-agent budget from class 5.3 (Memory for agents), applied to one agent on a team.
Summed over the teamThe team's input cost is this total over every call of every agent, which is the double sum from class 6.1 (Multi-agent architectures). \(T_{context}\) is the term that grows round by round, and the only one a context function controls.

Technique 2Hand off a note, not the transcript

When one agent passes work to the next, send a short structured note. This is the compaction from class 5.3 (Memory for agents), applied between agents instead of within one.

FactsOnly the sentences that carry a cited claim. The reasoning that led there stays behind.
SourcesThe ids behind those facts, checked against what the agent actually retrieved.
Open questionsWhat the agent could not find, so the next agent does not assume it was covered.

What a note looks likeA researcher's handoff on mortgage interest

handoff note (example)
## acquisition debt limit
- Interest is deductible on up to 750,000 dollars of acquisition debt taken on after December 15, 2017 [p936-2025-limit].
- Points paid to buy a main home are often deductible in the year paid [p936-2025-points].
sources: p936-2025-limit, p936-2025-points
open: nothing found on home equity loans used for repairs
What was droppedThree searches, their full results, a failed glossary call, and the model's reasoning. Several hundred tokens became about fifty.
What was keptEvery claim still has its id, so the writer can cite it and the reviewer can check it.

Measure itThe compression ratio, and keeping sources

$$r = \frac{T_{handoff}}{T_{raw}}$$

Every symbol\(T_{handoff}\) is the token count of the note you send; \(T_{raw}\) the token count of the transcript you would otherwise forward. Smaller \(r\) means more compression: \(r = 0.1\) sends a tenth.
Compression is lossySo decide what must survive. Source ids always do: a fact without its id cannot be cited downstream. The build also flags any id the researcher cited but never retrieved, a cheap catch for a made-up citation.

Technique 3Context pollution lowers quality

Extra context is not neutral. The model attends to whatever is in front of it, so irrelevant text competes with the text that matters.

StaleAn old draft or last year's figure (the 2024 limit sitting next to the 2025 one) invites the model to mix them.
IrrelevantSearch results for the other researcher's focus pull the answer off topic.
BuriedModels use information at the start and end of a long context better than in the middle (Liu and colleagues, "Lost in the Middle", 2023).

Pollution with intentRaw tool output must not travel between agents

Why it matters on a teamClass 5.6 (Reliability and failure modes) labeled tool output as untrusted inside one agent. Forwarding a transcript carries that untrusted text into the next agent's prompt, where the label may be gone and the agent may have more permissions.
The note is a filterA handoff note contains only the researcher's own cited claims, never the pages it read. That narrows what an injected instruction could reach. Class 6.5 (AI security) attacks this boundary directly.

Misconception"Give every agent everything, to be safe"

It feels safe because nothing is missing. In practice it costs more and answers worse.

CostEvery round rereads a growing pile. On a free tier the tokens-per-minute cap arrives sooner, and the team waits on 429 retries.
QualityMore distractors, stale numbers, and buried facts. Less, well-chosen context is the safer choice. The test that settles it is a quality check run on both versions, which the build does.

Technique 4How Groq prompt caching works

Property
What it means for you
Automatic
No setting. On gpt-oss models, a request whose start matches a recent request token for token reuses that prefix. Hits are likely, not guaranteed.
Expires
A cached prefix is dropped after 2 hours without use.
Exact prefix
Matching stops at the first differing token. Everything after it is computed fresh.
Minimum length
Model dependent, roughly 128 to 1024 tokens. Shorter prefixes are never cached.
Cheaper
Cached input tokens are billed at half price (at time of writing).
Rate limits
Cached tokens do not count toward the rate limits, which eases the free-tier caps. They are still subtracted after processing, so a burst of large parallel requests can hit the cap anyway.
Measured
usage.prompt_tokens_details.cached_tokens, recorded per call by the Module 6 llm.py.

The ruleStable content first, variable content last

Both prompts carry the same parts. Only the order differs, and the order decides what can be cached.

One character is enoughA timestamp or request id on line one changes the first token, so nothing after it ever matches. This is one of the most common caching mistakes.

Applying the ruleWhat goes in the prefix, what goes last

Prefix: identical on every callShared team rules, the agent's role, tool schemas, fixed examples. Write them once as constants, never with f-strings that insert a value.
Tail: changes per callThe notes, the draft, feedback, the question, and any time or request id you need. Put the id in a log, or at the very end if the model must see it.
Across agents tooWhen several agents open with the same shared rules, the same prefix is reused. Keep the shared block byte for byte identical: one agent with an extra space at the top breaks the match for itself.

What caching savesThe saving, in one line

$$\Delta C = c \cdot p_{in} \cdot 0.5$$

Every symbol\(c\) is the number of cached input tokens, read from cached_tokens; \(p_{in}\) the price per input token; 0.5 the discount, since cached tokens cost half. \(\Delta C\) is the money saved compared with paying full price for those tokens.
Worked example (illustrative)20,000 cached tokens at \(p_{in}\) = 0.075 dollars per million: \(20{,}000 \times 0.075 \times 10^{-6} \times 0.5\) = 0.00075 dollars. Small in money. The bigger free-tier gain is that those 20,000 tokens did not count toward the 8K-per-minute cap.

Caching outside the modelMemoization and shared retrieval

Memoize tool resultsIf a tool is called again with the same arguments, return the stored result. Safe for pure lookups like retrieval over a fixed corpus; wrong for anything whose answer changes, such as a live price or an inbox.
Share it across the teamOne memo behind every researcher means two agents that search the same thing pay once. The build normalizes the query (case and spacing) before looking it up.
Be honest about the hit rateMemoization only helps when queries repeat. On a two-question run the count is often zero or one. It pays off on long sessions and many users asking similar things.

Read your run carefullyThree things that can surprise you

Cached is 0 for an agentIts stable prefix is below the model's minimum cacheable length, or it was called only once. Do not pad the prompt to force a cache hit.
Quality fails in one modeThen the saving does not count. Check what the note dropped: usually a fact without its id, or an open question the writer ignored.
Numbers vary run to runThe model chooses different searches and drafts. Compare the size of the change, not the exact count, and run more than once before concluding.
