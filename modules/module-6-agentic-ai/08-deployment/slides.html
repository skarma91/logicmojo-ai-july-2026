Concept 1Docker: the shipping container for software

Before containers"It works on my machine." The server has a different Python, a missing system library, a different version of NumPy. Every deploy is a new debugging session.
The analogyA shipping container has one standard shape, so the same box loads onto any ship, train, or truck without repacking. A container image bundles your code, Python, and every library, so the same image runs on your laptop and on Render.
What it does not doA container is not a virtual machine: it shares the host's kernel and starts in seconds. It also does not make code correct; it makes environment problems disappear so the remaining problems are yours.

Three wordsImage, container, layer

Word
What it is
Analogy
Image
a read-only snapshot: base system, Python, libraries, your code, the start command
the packed container, sealed
Container
a running instance of an image, with its own process and a temporary writable layer
the container, opened at its destination
Layer
each Dockerfile step adds one; unchanged layers are reused from cache on the next build
boxes stacked inside, repacked only from the first change up
Why layers matterDocker rebuilds from the first changed layer upward. Put what rarely changes (dependencies) before what often changes (your code), and most rebuilds take seconds instead of minutes.

The recipeA minimal Dockerfile, line by line

example: a small notes API
FROM python:3.12-slim                # a small official base: Debian plus Python
WORKDIR /app
COPY requirements.txt .              # dependencies first: their own cached layer
RUN pip install --no-cache-dir -r requirements.txt
COPY . .                             # code last: edits only rebuild from here
USER nobody                          # do not run as root
CMD ["sh", "-c", "uvicorn app:app --host 0.0.0.0 --port ${PORT:-8000}"]
0.0.0.0, not 127.0.0.1Inside a container, localhost means the container itself. Listening on all interfaces is what lets traffic from outside reach the app.
$PORTHosts tell the app which port to use through an environment variable. Read it; do not hard-code one.

What stays outThe .dockerignore file

Like .gitignore, for the buildCOPY . . copies everything in the folder unless .dockerignore excludes it. Without one, your .env with real keys, local caches, and a virtual environment end up inside the image.
What the build excludes.env, __pycache__, logs and traces, local embedding caches (they would be stale), and .git. Smaller images build faster, push faster, and leak nothing.
A leaked key is foreverAnyone who can pull an image can read every file in every layer, including files a later step deleted. If a key was ever baked in, rotate it.

One image, many environmentsBecause configuration comes from the environment, the same image becomes "local", "staging", or "production" with different variables, and nothing is rebuilt.

The image dietFitting a team into 512 MB

Drop PyTorchsentence-transformers pulls in PyTorch, which alone can exceed the free tier's 512 MB. FastEmbed runs the same MiniLM model on the ONNX runtime with no PyTorch at all.
Bake the vectorsEmbed the corpus once, at image build time, and ship the vectors inside the image. At request time only the query is embedded.
One processThe class 5.5 (MCP) glossary server would load a second copy of the model in a second process. In the container, the same tool interface runs in-process.
Measured at authoring timeThe service with every library loaded uses about 118 MB before model weights; the MiniLM ONNX model is about 90 MB on disk. Confirm the real figure in the host's memory metrics after deploying.

A general ruleDo slow work at build time, not at request time

Why it matters on a free tierA sleeping service wakes on the next request. Every second of startup work is a second that user waits, on top of the minute the platform takes to wake.

Concept 2FastAPI: the early teaser, now built

Endpoint
What it does
POST /chat
runs the request through the gateway and the team; returns one JSON answer with outcome, sources, model used, cache hit, trace id, and token usage
POST /chat/stream
the same work, sent as Server-Sent Events: progress per graph step, then the final answer
GET /health
answers instantly with no model call, so the host can tell the service is alive
GET /docs
free with FastAPI: interactive documentation generated from the Pydantic models

Class 1.5 (APIs and the web) called an API; now we serve one.

ShapesPydantic models define the contract

The requestOne field, question, from 1 to 2,000 characters. An empty or oversized question gets 422 Unprocessable Content before any model is called: the cheapest guardrail there is.
The responseTyped fields: outcome, answer, route, pii_redacted (the kinds, never the values), model, cached, trace_id, usage, latency_s. Clients can rely on every one.
The trace id is for supportWhen a user reports a bad answer, the trace id in their response opens the exact run in LangSmith (class 6.6, Observability and tracing). No guessing which request it was.

ConcurrencyAsync endpoints, blocking work, and a semaphore

The event loopAn async endpoint runs on one event loop that juggles many requests, switching whenever one waits. It must never be blocked.
Blocking work goes to a threadThe team makes blocking model calls. asyncio.to_thread runs each request's team in a worker thread, so the loop keeps serving health checks and other clients.
A semaphore caps the workasyncio.Semaphore(2) lets two team runs proceed at once; the rest wait their turn. That keeps the shared Groq quota from being hit by ten parallel teams.
Per-request stateConcurrent requests must not share settings. The build keeps each request's model choice and budget in context variables, which every thread sees separately.

StreamingServer-Sent Events: progress while the team works

A team run takes seconds. Instead of a blank wait, the server sends small events as the graph moves: accepted, each step, then the final answer. The connection stays open until the last event.

HowFastAPI's EventSourceResponse: the endpoint yields events. The team runs in a thread and pushes each graph step into a queue the endpoint drains.

Staying upHealth checks

What the host does with itRender calls /health during deploys and while running. A new version only receives traffic once its health check passes, so a broken build never replaces a working one.
Keep it cheap and honestNo model call (it would cost quota and fail when Groq is slow). Do check what the service needs to start: the index is loaded, the configuration is present.
Liveness versus readinessLarger platforms separate "the process is alive" from "it can serve traffic". For one small service, a single cheap check that the index loaded covers both.

Concept 3What Render is

A cloud hosting platform: you hand it a Git repository or a Dockerfile, and it builds your code, runs it on its servers, and keeps it running.

Render handles
  • A build on every push
  • HTTPS certificates
  • Health checks, logs, metrics
  • Secrets as environment variables
You still own
  • The code and the Dockerfile
  • The image size
  • The plan, and so the bill
  • Keys and cost controls
Versus a raw server
  • An AWS EC2 machine gives full control
  • You patch the OS and set up networking and certificates
  • Render trades control for no operations work

Infrastructure as coderender.yaml, and the one line not to forget

services:
  - type: web
    runtime: docker
    plan: free              # omitted means a paid instance
    healthCheckPath: /health
    envVars:
      - key: GROQ_API_KEY
        sync: false           # asked for at setup, never stored in Git
Why a fileThe service's settings live in Git next to the code: reviewed, versioned, and repeatable. Clicking through a dashboard is none of those.
The trapIf plan is omitted, Render creates a new web service on a paid instance type. On a free course budget, that line is the difference between zero and a bill.

What free meansSleep, wake, and the 750-hour budget

$$31 \text{ days} \times 24 \text{ hours} = 744 \text{ hours} \;\le\; 750 \text{ free hours}$$

SleepAfter 15 minutes with no traffic, a free service spins down and uses no hours.
WakeThe next request wakes it in about a minute. The first user after a quiet spell waits; everyone after that does not.
The budget750 instance hours per workspace per month: one service awake all month fits. Two always-awake services do not.

The disk is temporary (lost on every sleep and redeploy), so keep traces in LangSmith, not local files.

Other hostsWhy not Hugging Face Spaces, and the AWS footnote

Hugging Face Docker SpacesDocker Spaces now require a paid PRO plan. If you already have one, the same image runs there unchanged: that is the point of a container.
AWS and the big cloudsWhen an employer pays, the same image runs on AWS App Runner, ECS, or the equivalent on other clouds, with scaling and no sleep. It is optional for this course and never free at scale.
The portable partA Dockerfile, environment variables for configuration, a health check, and a $PORT listener. Every host above accepts exactly that.

Rate limitingThe token bucket

$$\text{tokens}(t) = \min\big(b,\ \text{tokens}(t_0) + r\,(t - t_0)\big)$$

Every symbol\(b\) is the bucket's capacity, \(r\) its refill rate in tokens per second, \(t_0\) the last time it was checked. A request is served only if at least one whole token is available, and it removes one.
What it guaranteesBursts of up to \(b\) requests pass at once, so normal use feels instant. Over any long window of \(T\) seconds, at most \(b + rT\) requests pass, so the long-run rate stays at \(r\).

The build's defaults, \(b = 5\) and \(r = 0.1\) per second: five quick questions, then one every 10 seconds; a refusal is a 429 with Retry-After.

SizingConcurrency follows from the provider's limit

$$\text{requests per minute} \;\le\; \frac{\text{provider RPM}}{\text{model calls per request}} = \frac{30}{5} = 6$$

Every termProvider RPM is the requests per minute your plan allows (about 30 on Groq's free plan at time of writing). Each team request makes about five model calls (classifier, supervisor, researcher, explainer, supervisor), so the service can finish about six requests a minute in total.
What followsA concurrency limit of 2 keeps bursts from tripping the provider's limit, and a per-client rate of six a minute keeps one client from taking it all. More capacity means a paid plan or a local model, not a bigger semaphore.

Two cheap winsRouting and caching, done carefully

Route by a rule you can readLong, multi-part, or comparative questions ("compare", "versus", more than one question mark) go to gpt-oss-120b; everything else to gpt-oss-20b. A transparent rule is easy to test and to explain; replace it with a classifier only when the rule demonstrably fails.
Cache safelyKey the cache on the redacted, normalized question, so no personal data sits in it and trivial differences share one entry. Pick the time-to-live from how fast the answers change: tax rules change yearly, live prices by the minute.
What not to cacheRefusals that depend on context, answers built from a user's own data, and anything a later policy change should alter immediately. The build caches only successful answers.

After launchMonitoring in production

TracesLangSmith traces every request (class 6.6, Observability and tracing), with PII redacted first. Each response carries its trace id.
Logs and metricsThe host shows logs, memory, and CPU. Watch memory against the 512 MB limit, and 429 counts against the rate limits.
HealthThe health check, plus an outside uptime check if users depend on it.
QualitySample live runs and score them (class 6.7, Evaluating agentic systems); run the offline suite and its gate before every deploy.

Misconception"Deploying means paying for cloud"

A free web service plus Groq's free plan, or a local model, ships a real multi-agent system at no cost.

What free costs youA one-minute wake after idle, 0.1 CPU, 512 MB, a temporary disk, and a shared model quota. Real limits, all of which this build was designed around.
What free does not cost youCorrectness, safety, tracing, evaluation, or a public URL. Paying buys scale and uptime later; the engineering is the same.
