Print-debugging fails for agents

A team run is dozens of model calls, tool calls, and agent turns, some running at the same time, some looping. When it is slow, expensive, or wrong, print statements cannot tell you which step is to blame. A trace can.

The problemWhat print statements look like for a team

a support team's log (example)
calling model...
searching help articles for "refund window"
calling model...
got 3 results
model replied (412 tokens)
ERROR: billing lookup timed out
model replied (1,903 tokens)
Who said what?Two agents ran in parallel, so their lines interleave. Which model call made 1,903 tokens?
What caused what?Did the timeout break the answer, or did the team recover? The log has no parent and child.
Where did the time go?No durations, and no way to tell which waits overlapped.

The shiftA log is a list of lines. A trace is a tree of timed, attributed work. Every question above becomes a walk over that tree.

The shapeA trace is a tree

The root is the request. Its children are agent turns, and theirs are the model and tool calls each turn made. The tree answers "who said what" and "what caused what" by construction.

Parallel branches stay separateThe two agents ran at the same time, but each call sits under the agent that made it. Interleaving is gone.

ConventionsSpan kinds and names that stay useful

KindsLangSmith's run types are a good default: chain for a run or an agent turn, llm for a model call, tool for a tool call, retriever for a search. Kinds let you ask "how much time went to tools?" in one filter.
NamesStable and low-cardinality: llm:billing, not llm call at 14:02:11. Put the variable part (question, hop, focus) in inputs or metadata. Stable names are what make "cost share by span name" possible.
Instrument from outsideThe build wraps llm.chat, the retriever, the MCP bridge, and each graph node. The team's own code carries no tracing calls, the same idea as the class 6.4 (Guardrails, routing, and compliance) gateway.

Concept 2Total time and self time

$$T_{self}(i) = T(i) - \Big|\bigcup_{c \,\in\, \text{children}(i)} [\,s_c, e_c\,]\Big|$$

Every symbol\(T(i)\) is span \(i\)'s total duration. \([s_c, e_c]\) is child \(c\)'s interval, from start to end. \(\bigcup\) merges the children's intervals, and \(|\cdot|\) is the total length of the merged result. Self time is the part of the span not spent waiting on a child.
Why merge firstTwo children that ran at the same time cover the same seconds once, not twice. Subtracting their durations separately gives a negative self time. Merge the overlap, then subtract.

Wall timeThe critical path, not the sum

With parallel branches, the request takes as long as its longest chain of dependent steps. That chain is the critical path. Speeding up anything off it does not make the request faster.

In the figure (illustrative)The search takes 0.6 s while billing takes 1.8 s in parallel. Halving the search saves nothing; cutting billing by 1 s saves 1 s.

The algorithmWalking back from the last finisher

The walkAmong a span's children, start with the one that finished last. Step back to the child that finished last before it started: that is what it was waiting for. Repeat until nothing ended earlier, then do the same inside each chosen child.
What it gives youThe ordered list of spans that set the wall time. The build prints it next to the sum of all leaf spans; when branches overlap, the sum is larger than the wall time, and only the path matters for latency.
A caveatThe walk infers waiting from timestamps. It is right for the fork and join shapes in this module. Systems with queues or locks need explicit dependency links between spans.

Where the money goesShare of cost per span

$$s_i = \frac{c_i}{\sum_j c_j}$$

Every symbol\(c_i\) is the cost of span \(i\), from its tokens and the model's prices (cached input at the cached price). The sum runs over every span in the run. \(s_i\) is span \(i\)'s fraction of the total; the shares add up to 1.
Worked example (illustrative)A run costs 0.40 cents: the billing agent's two calls 0.26, the writer 0.09, triage 0.05. Billing's share is \(0.26 / 0.40 = 65\%\). Halve the writer's cost and the run gets 11% cheaper; halve billing's and it gets 33% cheaper.

Class 5.7 (Assemble a single agent) showed that agent runs are expensive; the largest share names the exact span where tuning pays.

Two bottlenecksThe slowest span is rarely the costliest

Slowest: a latency fixOften a tool: a slow lookup, a cold service, a retry wait. Fix it with a timeout, a cache, or by moving it off the critical path into a parallel branch.
Costliest: a token fixAlmost always a model call with a large prompt, usually late in a loop where context has piled up. Fix it with scoped context and compressed handoffs from class 6.3 (Context engineering), or a smaller model.
Rank by the right measureRank latency by self time on the critical path. Rank cost by share. A span that is both slow and costly, on the critical path, is the first thing to fix.

Failures in a traceErrors, retries, and loops that cannot win

A failed spanA span can fail while the run recovers (the model reads the error and tries another tool). The trace keeps both facts: the error, and what happened next.
The repeated identical errorThe same tool, the same arguments, the same error, three times. Nothing changed between attempts, so nothing could succeed. In a trace this pattern is visible at a glance.
Growing cost per retryEach retry carries the history of the last, so model spans get more expensive as the loop goes on. The micro-assignment measures exactly this.
Symptom versus causeThe root's error ("hop cap reached") is the symptom. The first failed child is the cause. Read failures from the earliest one, not from the top.

Concept 3Structured feedback: a key, a score, a comment

run 7f2c...   key=resolved_without_handoff   score=0   comment="customer asked for a human"
run 7f2c...   key=cites_policy   score=1   comment="quotes refund policy section 3"
Attached to the runFeedback is stored with the trace it judges, so a low score leads straight to the spans that produced it. In LangSmith that is one call: create_feedback(run_id, key, score, comment).
Keys are questionsA good key is one yes-or-no question you will ask of many runs. Then scores can be averaged, compared between versions, and charted over time.

Concept 4Setting up LangSmith

Four steps
  • Sign up at smith.langchain.com with Google, GitHub, or email. No credit card for the free plan.
  • Settings, then API Keys, then Create API Key. Copy it once.
  • Add the variables to .env.
  • Run the build, then open Tracing and choose the project.
LANGSMITH_TRACING=true
LANGSMITH_API_KEY=<your key>
LANGSMITH_PROJECT=genai-course-6-6
# outside the US region only:
LANGSMITH_ENDPOINT=https://eu.api.smith.langchain.com
The region trapA non-US account without LANGSMITH_ENDPOINT fails to authenticate, and the error does not say "wrong region". If traces never appear, check this first.

What gets tracedAutomatic for the graph, explicit for your code

AutomaticOnce LANGSMITH_TRACING=true is set, LangGraph and LangChain report their own steps: graph nodes, chains, and calls made through their model wrappers.
ExplicitCalls that bypass those wrappers (our llm.py talks to Groq directly) and plain Python functions need spans of their own: the @traceable decorator, or the trace() context manager the build uses.
Both nest togetherLangSmith tracks the current span in a context variable, so a span you open inside a LangGraph node appears under that node, even across parallel branches.

PrivacyTraces leave your machine: redact first

What a trace containsEvery prompt, every retrieved passage, every answer. Sent to LangSmith, that is a third party holding a copy of your users' requests, which is exactly the data flow class 6.4 (Guardrails, routing, and compliance) mapped.
What the build doesEvery input and output passes through the redactor from class 6.4 (Guardrails, routing, and compliance) before it is recorded, locally or remotely, then is truncated to 600 characters. A trace shows <EMAIL_1>, never the address.
Also considerWho on the team can open traces, how long they are kept, and whether a user's erasure request reaches the trace store too.

In productionVolume, sampling, and retention

VolumeOne team request can produce 30 or more spans. At real traffic, tracing everything costs storage and money, and may exceed a plan's trace allowance.
Sample, but keep failuresTrace a fraction of successful runs and every run that errors or scores badly. The interesting traces are the rare ones.
RetentionOn LangSmith's free plan, traces are kept 14 days at time of writing. Export the ones you need, for example as evaluation examples.
