Concept 1Right answer, wrong path

Path wrong

Why the top-right cell matters mostAn answer-only evaluation counts it as a pass. It is the most dangerous cell: it looks healthy and fails as soon as the question changes slightly.

The object we scoreWhat a trajectory is

a travel team's run (example)
request    "Can I change my Lisbon flight to Friday without a fee?"
trajectory booking_agent > tool:find_booking > tool:fare_rules > policy_agent > tool:change_policy
reference  booking_agent > tool:fare_rules > policy_agent
Steps are workA trajectory is the ordered list of worker-agent turns and tool calls a run made, read straight from its trace (class 6.6, Observability and tracing).
Routing is left outSupervisor turns decide who works next; they are not work. Including them would make every reference depend on how many times the supervisor was consulted.

The usual choice: in-orderAgents legitimately take extra steps (an extra lookup, a clarifying search). In-order checks what must happen, and in what sequence, without punishing harmless detours.
When order does not matterTwo independent lookups in parallel can finish in either order. Use set matching for those steps, or both orders in the reference.

The mechanismAn in-order match, step by step

Walk the actual steps once, left to right. Each time a step equals the next required one, tick it and move on. The match passes if every required step gets ticked.

One pass, no backtrackingOnce a required step is matched, earlier actual steps cannot be reused. That is what enforces order.

Grading the pathStep precision and recall

$$P = \frac{|T_{act} \cap T_{ref}|}{|T_{act}|} \qquad R = \frac{|T_{act} \cap T_{ref}|}{|T_{ref}|}$$

Every symbol\(T_{act}\) is the multiset of steps the run took; \(T_{ref}\) the steps the reference requires. \(\cap\) keeps each step as many times as it appears in both. \(|\cdot|\) counts steps. \(P\) is precision, \(R\) is recall.
What each one catchesLow precision: wasted steps, which cost tokens and time. Low recall: skipped steps, which risk a wrong answer. A pass needs recall of 1 on the required steps; precision is a cost signal.

Worked examplePrecision and recall on the travel run

The run aboveFive steps taken, three required, all three present. \(P = 3/5 = 0.6\): two of five steps were not needed. \(R = 3/3 = 1.0\): nothing required was skipped. In-order match passes.
Why multisetsSuppose the run called fare_rules twice. With sets, both copies count as one, and precision hides the waste. With multisets, one copy is useful and the other is waste: \(P\) drops, as it should.
Skipped versus extraA run of just booking > policy has \(P = 1.0\) and \(R = 2/3\). Perfect precision, failing path: precision alone would call this run efficient.

Concept 2Tool-use correctness

Right tool, right orderCovered by the trajectory: the required tool calls appear, in order.
Valid argumentsEvery call matches the tool's schema: required fields present, right types, nothing empty. A call that fails validation is a bug even if a retry fixes it.
Expected valuesFor the tools a task cares about, check the arguments themselves: exactly "LIS" for the airport, or a query that mentions "change fee".
No redundant callsThe same tool with the same arguments twice in one run is pure waste: its second answer cannot differ from the first.

Prefer state over proseWhen the system acts (books, files, updates), check the resulting state, not the message that claims it.
When prose is all you haveCheck concrete facts and citations deterministically, and use a model judge (class 4.8, Evaluating LLM and RAG) only for what cannot be checked exactly.

Honest numbersA pass rate is an estimate

$$\hat p \pm 1.96\sqrt{\frac{\hat p\,(1-\hat p)}{n}}$$

Every symbol\(n\) is the number of tasks; \(\hat p\) the share that passed. The square root is the standard error: how much \(\hat p\) would wobble on a different task set. 1.96 makes the range cover the true rate 95% of the time.
Worked example24 of 30 tasks pass: \(\hat p = 0.8\), standard error \(\sqrt{0.8 \times 0.2 / 30} \approx 0.073\), so \(0.8 \pm 0.14\). The true rate could be anywhere from 66% to 94%.

On 30 tasks a three-point change is one task: do not celebrate it, and do not panic about it.

Small setsWhere the simple interval breaks, and Wilson's fix

The failureAt 8 of 8, \(\hat p = 1\) and the formula above gives \(1 \pm 0\): it claims certainty from eight tries. Near 0 or 1, and for small \(n\), the simple (Wald) interval is too narrow.
The Wilson score intervalA short formula with the same inputs that stays sensible at the edges. For 8 of 8 it gives 68% to 100%: "probably good, not proven". The build and the micro-assignment print both intervals.
Practical ruleReport the interval, not just the rate. If two versions' intervals overlap heavily, the evaluation cannot tell them apart yet; add tasks before deciding.

Sizing the setHow many tasks do you need?

$$n \approx \left(\frac{1.96}{h}\right)^{2} p\,(1-p)$$

Every symbol\(h\) is the half-width you want (0.05 for "within five points"); \(p\) your expected pass rate. It is the interval formula solved for \(n\).
Worked exampleAt \(p = 0.8\): within ten points needs about 62 tasks; within five points about 246. Halving the interval costs four times the tasks, and four times the model calls.

A gate of 20 to 60 well-chosen tasks catches pinned regressions; precise rates need hundreds, which is what online monitoring is for.

Concept 4Offline sets and LangSmith experiments

An offline setA fixed list of tasks, each with a reference trajectory, expected arguments, and a success check. It runs before every change: same tasks, so differences come from the change.
The production formIn LangSmith the task list is a dataset, each run of the system over it is an experiment, and the scorers are evaluators. Experiments are compared side by side, task by task.
Keep a holdoutIf you tune prompts against the same tasks you gate on, the gate measures memorization. Keep some tasks out of sight, as the Module 6 milestone does with a 20% holdout.

After you shipOnline monitoring

Sample live trafficScore a fraction of real runs, and every run that errors. Real users ask things no offline set predicted.
Score without referencesLive runs have no reference trajectory. Use reference-free checks: cited sources exist, no forbidden steps, budget respected, plus a model judge and user feedback from class 6.6 (Observability and tracing).
Feed the offline setEvery surprising live failure becomes a new offline task, with its reference written by a person. The set grows from real mistakes.

Turning evals into a guardRegression gates

Pin what passedEvery task that passed in the trusted baseline is pinned. A change that makes any pinned task fail is blocked, and the gate names the tasks.
Automate itRun the suite in CI on every change and exit with a non-zero status on a regression. A gate that someone has to remember to run is not a gate.
Pinned tasks versus the pass rateThe rate is noisy (see the intervals), so do not gate on a small change in it. Pinned tasks are not noisy in the same way: a task that passed reliably and now fails is a specific, investigable change.

The whole loopEvaluation as part of shipping

Misconception"If the answer is right, the system is fine"

A right answer by a broken path fails on the next input. The path is what generalizes.

What answer-only missesA model that answers from memory instead of searching, a forbidden step that happened not to hurt, a tool called with a typo that a retry fixed. Each passes an answer check today.
What the build showsIt prints the pass rate next to the answer-only rate. The gap between them is exactly the set of runs an answer-only evaluation would have waved through.

In practiceWhere good tasks come from

Real requestsSample from traces, so the set looks like what users actually ask. Redact first (class 6.4, Guardrails, routing, and compliance).
Known failuresEvery bug you fix becomes a task, pinned, so it cannot come back unnoticed.
Deliberate edge casesAmbiguous names, missing data, a request that needs no tools at all, one that needs every tool.
Writing the referenceList only the steps that must happen, not everything a good run did. An over-specified reference fails legitimate runs and teaches people to ignore the gate.
