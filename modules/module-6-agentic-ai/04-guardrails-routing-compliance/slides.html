The design principleThe team's code does not change at all. Every rail lives outside it, so there is one place to read, test, and audit.

An analogySecurity before the gate, customs on the way out

Input guard: airport securityChecks every request before any agent sees it. It stops what must never board: disallowed requests, prompt attacks, oversized pastes. It is cheap per passenger, so it runs on everyone.
Output guard: customsChecks the answer before the user sees it. It catches what slipped through or was created on board: personal data in the reply, or an answer with no source behind it.
Why bothAn input guard cannot see what the team will produce, and an output guard sees too late to save the cost of a bad run. Each catches failures the other cannot.

The shapeThe gateway, stage by stage

Design choiceWhy a wrapper, not rules inside each agent

One policy, one placeRules scattered across five agents drift apart. A gateway states the policy once, and every path obeys it.
Agents stay simpleEach agent does its job; none carries compliance code. Adding a sixth agent adds no new compliance surface.
One audit trailEvery decision, with its stage and reason, lands in one log. An auditor reads one file, not five agents' prompts.
What stays inside the agentsThe class 5.6 (Reliability and failure modes) rails: step caps, call validation, untrusted-output labels. The gateway does not replace them; it adds the team-level layer.

Concept 1Rules first, classifier second: the cost funnel

$$\mathbb{E}[C] = c_{rules} + (1 - b)\, c_{clf}$$

Every symbol\(\mathbb{E}[C]\) is the expected checking cost per request. \(c_{rules}\) is the cost of the local checks, close to zero. \(b\) is the share of requests the local stages settle (blocked, refused, or answered with a canned reply). \(c_{clf}\) is one classifier call. Only the remaining \(1 - b\) pay for it.
Worked example (illustrative)If local stages settle 40% of traffic, \(b = 0.4\), and the classifier runs on 60% of requests. At 10,000 requests a day that is 4,000 fewer model calls, and 4,000 fewer chances to hit a rate limit.

Ordering the stagesRoute before you classify

The build routes first and classifies only requests headed to the team. The refuse, canned, and fallback paths never reach a model, so a classifier call there buys nothing.

The ruleSpend the expensive check where the power is. The team can search, call tools, and write answers; a canned reply cannot do harm whatever the request says.
When to classify first insteadIf every path can act (each route leads to an agent with tools), the classifier must see everything, so it moves ahead of the router. The order follows from what each path can do.

Write the policyFour sections, about 400 to 600 tokens

policy excerpt (example: a pharmacy assistant)
## INSTRUCTIONS Classify one request to a pharmacy assistant. Return JSON: violation, category, rationale.
## DEFINITIONS Diversion: obtaining a prescription drug without a valid prescription.
## VIOLATES (1) Requests to get controlled drugs without a prescription (category "diversion").
## SAFE (0) Questions about side effects, dosage on the label, or store hours.
## EXAMPLES "Can I take ibuprofen with food?" gives {"violation": 0, ...}
Definitions do the workThe model judges against your words. A vague term ("harmful") gives vague verdicts; a defined one ("diversion: ...") gives consistent ones.
Examples set the boundaryInclude safe examples that look risky. They are what stops the classifier blocking legitimate questions.

When the check itself failsFail closed or fail open

Fail closedIf the verdict cannot be read, treat the request as a violation. Safer, but an outage blocks everyone. The build does this for unreadable verdicts.
Fail openIf the check is down, let the request through. Available, but an attacker who can break the check walks past it.
Decide per path, in advanceA path with tools fails closed; a read-only FAQ path might fail open. What matters is that you chose, wrote it down, and log every time it happens.

Measuring a guardTwo errors, two rates

$$\text{block rate} = \frac{\text{unsafe requests stopped}}{\text{all unsafe requests}} \qquad \text{false-block rate} = \frac{\text{safe requests stopped}}{\text{all safe requests}}$$

A missAn unsafe request gets through. The block rate falls. The cost is whatever the team then does with it.
A false blockA legitimate user is refused. The false-block rate rises. The cost is lost trust, and users learning to rephrase around the guard.
Measure both, on a labeled setA guard that blocks everything has a perfect block rate. Only the false-block rate shows it is useless. The build reports both.

The ideaEmbed the request (class 4.4, Embeddings and vector databases) and compare it with each route's examples. Paraphrases land close together even when they share no words.

The mechanismEach route is a centroid

Write four to six example utterances per route, embed them, and average each route's vectors. That average, the centroid, stands for the route. A new request goes to the centroid it points at most closely.

Re-normalize the meanThe average of unit vectors is shorter than one. Divide it by its length again, or cosine scores stop being comparable.

The ruleNearest centroid, if it is near enough

$$\text{route} = \begin{cases} \arg\max_r \cos(e_q, c_r) & \text{if } \max_r \cos(e_q, c_r) \ge \tau \\ \text{fallback} & \text{otherwise} \end{cases}$$

Every symbol\(e_q\) is the request's embedding. \(c_r\) is the centroid of route \(r\). \(\cos\) is cosine similarity, from \(-1\) to \(1\). \(\arg\max_r\) means "the route with the highest score". \(\tau\) (tau) is the lowest score we trust.
What the threshold buysWithout \(\tau\), every request goes somewhere, even "best pizza near me". With it, a request that is close to nothing gets a fallback reply instead of being forced into the nearest route.

TuningChoosing \(\tau\) from data, not by feel

The procedureScore a labeled set. Take the weakest best score among in-scope requests and the strongest among out-of-scope ones. If the first is higher, set \(\tau\) between them. The build's --tune flag does exactly this.
If they overlapNo threshold separates them. Moving \(\tau\) only trades misroutes for fallbacks. Fix the route examples instead: add paraphrases of the requests that scored low.
The trade-offA high \(\tau\) sends more real questions to the fallback (users rephrase). A low \(\tau\) forces odd requests into a route (wrong answers). Which is worse depends on what the route can do.

Concept 3Redact PII with typed placeholders

before I'm Ana Ruiz, reach me at ana.r@mail.test or 646-555-0188 about my refund.
after  I'm <PERSON_1>, reach me at <EMAIL_1> or <PHONE_1> about my refund.
Why typed placeholdersThe agent still knows what kind of thing was there ("the user gave a phone number") and can reason about it, without ever seeing the value. A blank or "[REDACTED]" loses that.
The vault stays homeThe mapping from placeholder to value stays in the gateway's memory. It is never logged, traced, or sent to a model. Only the edge may restore a value, and only for the person it belongs to.

Precision through validationA pattern finds candidates; a validator confirms

Luhn check, workedTake 7992 7398 713. From the right, keep one digit, double the next, and so on; a doubled digit above 9 loses 9. The digits become 3, 2, 7, 7, 9, 6, 7, 4, 9, 9, 7, which sum to 70. That is divisible by 10, so it passes. Change one digit and it fails. A random 16-digit order number fails nine times in ten.
Rules for US Social Security numbersThe 3-2-4 shape alone matches case numbers and part codes. Some ranges are never issued: area 000, 666, or 900 to 999; group 00; serial 0000. Rejecting those cuts false alarms at no cost in recall.
Order matters tooCheck the longest patterns first (cards before phone numbers) and never let two spans overlap, or one number gets masked twice with two different labels.

Measuring redactionPrecision, recall, and which one matters

$$\text{precision} = \frac{TP}{TP + FP} \qquad \text{recall} = \frac{TP}{TP + FN}$$

Every symbol\(TP\): real PII spans that were masked. \(FP\): harmless spans masked by mistake. \(FN\): real PII that was missed. Precision asks "of what we masked, how much was PII?" Recall asks "of the PII, how much did we mask?"
Worked example (illustrative)A text has 10 PII spans. The redactor masks 12 spans, 9 of them real. Precision is \(9/12 = 0.75\); recall is \(9/10 = 0.9\). The one missed span is the one that leaks into the log.

Which error to fearFor redaction, recall comes first

A false positiveAn order number gets masked as a card. The agent sees <CARD_1> where a harmless number was. Mildly annoying, and easy to spot in testing.
A false negativeA real Social Security number is missed. It is now in the log file, the trace store, and the model provider's request history, and it cannot be recalled from any of them.
The tuning orderWrite patterns broad enough to catch every real case, accepting some false alarms. Then add validators (Luhn, never-issued ranges) to remove false alarms without losing real ones. Measure both on a labeled set after every change.

The hard caseNames need a model; rules need cues

What rules can doFind a capitalized name right after a cue ("my neighbor", "patient", "my name is", "Dr."). That catches some names and misses the rest: "Thanks, Priya" has no cue.
What production usesMicrosoft Presidio combines pattern recognizers, validators, context words, and a named-entity model such as spaCy. It is the same detect, validate, replace idea, with a model for the cases rules cannot see.
In the buildOne request ends with a name and no cue. The redactor misses it, recall drops below one, and the compliance check finds that name in the audit log. The leak is deliberate. It shows exactly what rule-based redaction cannot do.

Concept 4: intuition, not legal adviceGDPR in four ideas

Idea
In plain words
What it means for an agent team
Data minimization
collect and keep only what the purpose needs
redact before logs and traces; do not store full chats by default
Purpose limitation
use data only for the reason it was collected
a support chat is not training data unless users agreed to that
Lawful basis
a valid reason to process, such as consent or a contract
know which basis covers each data flow, including the model provider
Right to erasure
people can ask for their data to be deleted
you must be able to find and delete it in logs, traces, and vector stores
NoteThis is the EU's General Data Protection Regulation, simplified. Obligations depend on where you and your users are; ask a qualified person for real decisions.

Health dataHIPAA intuition

Protected health informationHealth details tied to an identifiable person: a diagnosis plus a name, a visit date plus a record number. On its own, "braces are deductible" is not PHI.
Business associate agreementA US covered entity, such as a clinic, may share PHI with a vendor (including a model provider) only under a signed agreement that binds the vendor to protect it.
Minimum necessaryUse and share only the PHI a task needs. That is redaction again, required by rule.
Why the build refuses medical recordsA tax assistant has no agreement and no need. The router sends any request for someone's medical records to a refusal, before any agent or model sees it.

Follow the dataWhere personal data can leak in this system

Every arrow out of the gateway is a copy of the request leaving your control: to a model provider, a log file, a tracing service, or a vector store. Redaction sits before all of them.

The testFor each destination, ask: if this were breached tomorrow, whose data would be in it? The answer should be "nobody's".

The ordering ruleRedact before logging, tracing, or calling a model

The common mistakeLog the raw request "for debugging", then redact before calling the model. The model is clean, and the log holds every SSN users ever typed.
The build's checkAfter the run, the audit log is searched for every labeled raw value. A clean result is evidence, not hope. A hit names exactly which span the redactor missed.
Coming upClass 6.6 (Observability and tracing) sends traces to LangSmith, a third party. The same rule applies: span inputs pass through the redactor before they are recorded.

Misconception"Compliance is someone else's job"

Legal can tell you what is required. Only the architecture decides whether it is possible.

Bolted on laterRaw requests are already in logs, traces, and a vector store across three services. Erasure means a search through all of them, and some cannot delete a single record.
Designed inOne gateway redacts before every exit, logs only placeholders, and keeps the vault in memory. Erasure is mostly done before anyone asks.
