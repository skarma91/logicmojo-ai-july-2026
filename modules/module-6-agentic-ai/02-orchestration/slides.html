Mechanic 1Subgraphs: each worker is its own graph

A worker is a compiled LangGraph graph (class 5.4, LangGraph) used as a single step inside the team graph. The team sees its inputs and outputs; its internal loop, tool calls, and messages stay inside.

Why encapsulateThe team graph stays small and readable, each worker can be built and tested alone, and a worker's long scratch work never floods the team's state.
In the buildEach researcher is the class 5.7 (Assemble a single agent) agent (retriever, MCP glossary, guardrails), unchanged. The team calls it twice, with two different focuses.

Wiring a subgraphTwo ways to connect parent and child

Add it directly as a nodeWhen the child's state shares keys with the parent's, pass the compiled graph to add_node. Shared keys flow in and out automatically.
Call it from a wrapper nodeWhen the schemas differ (the usual case), a small node builds the child's input, calls child.invoke(...), and maps the result back. The build does this: it passes a task in and takes only the final findings out.
The rule of thumbThe wrapper is a translation layer. It is also where you decide what the child is allowed to see and what it returns, which is exactly the question class 6.3 (Context engineering) sharpens.

A design decision, not a defaultAsk of every field: does another agent need this to do its job? If not, keep it private.

Merging parallel writesReducers decide what happens

Append: Annotated[list, operator.add]Both parallel researchers write findings; the reducer appends, so both results survive. Use it for anything parallel workers contribute to.
Overwrite: a plain keyThe latest value replaces the old one. Right for draft: only the newest draft matters.
What happens if you forgetTwo parallel branches writing a plain key do not silently lose one update. LangGraph refuses: InvalidUpdateError: At key 'findings': Can receive only one value per step. The fix is a reducer. We triggered this deliberately to confirm it.

The trade-offToo much sharing versus too little

Too muchEvery agent reads everyone's raw work. Prompts grow, cost rises, and the model attends to irrelevant detail. A writer does not need the researcher's twenty retrieved passages, only the findings.
Too littleAn agent lacks what it needs and guesses, or calls a tool again to recover information another agent already had. The reviewer, for instance, must see the notes to check the draft against them.

The right amount is "exactly what this agent's job needs". Class 6.3 (Context engineering) turns that into a measured technique.

Mechanic 3Fan-out and fan-in with Send

A routing function returns a list of Send("researcher", payload) objects, one per independent task. LangGraph runs them in the same step, in parallel. The merge node runs once, after all of them finish.

Each Send carries its own inputHere: the question plus a focus. The researcher node receives only that payload, not the whole team state.

Why parallelizeSequential versus parallel latency

$$L_{seq} = \sum_{i=1}^{m} \ell_i \qquad\qquad L_{par} \approx \max_{i} \ell_i + \ell_{merge}$$

Every symbol\(m\) is the number of independent workers, \(\ell_i\) the time worker \(i\) takes, and \(\ell_{merge}\) the time to combine results. Sequential waits for each in turn; parallel waits only for the slowest.
Measured in the buildThe timeline prints both: the researchers' durations summed (what sequential would cost) and the span they actually took. With two equal workers, parallel roughly halves the wait. The figure on the build slide is illustrative.

The honest caveatRate limits cap real parallelism

Parallel branches send their requests at the same moment, which is exactly what a rate limit punishes. On Groq's free plan (at time of writing about 30 requests and 8K tokens per minute for gpt-oss-20b), a wide fan-out stalls on HTTP 429 and the parallel speedup disappears.

Keep the fan-out narrowTwo or three branches is comfortable; ten will mostly wait. Throttle the width to what your tier allows.
Back off, with jitterThe Module 6 llm.py retries on 429 with a little random jitter, so parallel branches do not all retry at the same instant and collide again.

Mechanic 4, part 1Conditional routing

A conditional edge reads the state and returns the next node's name (class 5.4, LangGraph), now at team scale: send a request to the right specialist, or send a draft back for revision.

Route on a field, not on proseThe build routes on state["approved"], a boolean set from a structured verdict. Parsing "looks good to me" out of free text is fragile; reading a field is not.
Every route needs an exitThe routing function also checks the round count. Routing that can always send work back is a loop with no guaranteed end.

Mechanic 4, part 2The reviewer-writer loop

The writer drafts from the merged notes. The reviewer checks the draft and either approves it or sends it back with specific fixes. The writer revises using that feedback, and the loop repeats until approval or the round cap.

The exit is mandatoryApproval or at most three rounds: the step cap from class 5.6 (Reliability and failure modes), applied to a team loop.

How many rounds?Expected iterations of a bounded loop

If each revision passes review with probability \(q\), and the loop stops at \(k\) rounds at most, the expected number of rounds is:

$$\mathbb{E}[\text{rounds}] \;=\; \sum_{j=0}^{k-1}(1-q)^j \;=\; \frac{1-(1-q)^k}{q}$$

Every symbol\(q\) is the chance a single draft passes; \(k\) the round cap; \((1-q)^j\) the chance the first \(j\) drafts all failed, which is when round \(j+1\) happens. Without a cap the mean is \(1/q\).
Worked example (illustrative)\(q = 0.5\), \(k = 3\): \((1 - 0.125)/0.5 = 1.75\) rounds on average. Each round costs a writer call and a reviewer call, so the loop's cost scales with this number.

Make the reviewer usefulStructured verdicts, and exact checks first

A verdict tool, not proseThe reviewer calls a verdict tool with approve (true or false) and feedback (specific fixes), with tool_choice="required". The router reads a boolean; the writer reads concrete instructions.
Exact checks override the LLMBefore trusting the model's opinion, run what can be checked exactly: the word limit, and whether every cited source id really appears in the notes. If an exact check fails, the draft is not approved, whatever the LLM said.
Specific feedback converges"Cite the limit's source" gets fixed in one round. "Make it better" can loop until the cap, because the writer cannot tell what to change.
