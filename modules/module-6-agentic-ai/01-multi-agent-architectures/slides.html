The case for a teamWhen splitting the work pays off

Distinct rolesThe task has real stages with different jobs: research the facts, write for a reader, check the result. Each agent gets a focused prompt and only the tools for its job.
ParallelismIndependent parts can run at the same time: two researchers on two sub-questions, then a merge. Covered properly in class 6.2 (Orchestration).
Context isolationEach agent keeps its own context window, so one agent's long tool output does not crowd another's reasoning. Class 6.3 (Context engineering) builds on this.
Also: different privilegesA worker that reads untrusted documents should not hold a tool that sends email. Splitting roles lets you split permissions, which class 6.5 (AI security) turns into a defense.

An analogyThe newsroom versus the solo reporter

The newsroom wins on an investigationA reporter digs, an editor shapes the story, a fact-checker verifies every claim. Separate roles catch errors one person would miss, and the work moves in parallel.
The solo reporter wins on a correctionFixing a typo in a two-line story does not need a meeting. Routing it through three desks adds handoffs, delay, and chances to garble the fix.

Agents are the same. A team earns its overhead only on tasks big or varied enough to need distinct roles.

Misconception"More agents is more capable"

It is not. Every agent added brings more calls, more tokens, more handoffs, and more places to fail. A committee of fragile agents often loses to one agent with good tools.

What a team addsA coordinator's calls on top of every worker's, messages passed between agents, and a new class of bug: the right worker never gets asked, or the wrong one does.
The ruleComplexity is a cost, not a feature. Add an agent the way you would add a microservice: when a specific need justifies the operational price.

Pattern 1Supervisor: a coordinator delegates and combines

One coordinator agent decides which worker acts next, passes it the work, reads the result, and decides again: delegate, collect, repeat, finish. It is the class 5.1 (What is an agent) loop, one level up, where the "tools" are other agents.

Worked example"Explain my HSA limit simply." The supervisor sends the tax researcher to find the limit, then the explainer to rewrite it, then finishes. For "What does AGI mean?" it skips the explainer.
Strengths and risksFlexible: the path adapts per request. The supervisor is also a single point of failure and pays a model call at every hop, so cap the number of hops.

Two ways to delegateAgent-as-tool versus handoff

Agent-as-toolThe supervisor calls a worker exactly like a function tool (class 5.2, Tool calling and ReAct): it sends a request, gets an answer back, and stays in charge. Simple, and the supervisor sees every result.
HandoffControl moves to the worker, which acts and then hands back (or onward). In LangGraph a node returns Command(goto="worker") to transfer control. Today's build uses handoffs.
Prebuilt versus hand-builtLangGraph offers a prebuilt supervisor (the langgraph-supervisor package). We build ours by hand so every routing decision is visible; reach for the prebuilt once you know what it does.

Pattern 2Hierarchical: supervisors of supervisors

When one coordinator would have too many workers to choose between, group them into sub-teams, each with its own supervisor, and put a lead supervisor on top. It is the org chart applied to agents.

When it fitsLarge tasks with natural divisions: a research sub-team and a writing sub-team, each coordinating its own specialists.
The costEvery level adds coordination calls and latency, and a mistake at the top cascades down. Use it only when a flat supervisor cannot manage the choice.

Pattern 3Pipeline: a fixed sequence, and that is fine

Each agent's output feeds the next in a fixed order: research, then write, then review. No coordinator decides the order, because you wrote it.

It is a workflowBy the definition from class 5.1 (What is an agent), a fixed order is a workflow, not an agent deciding its own path. That is often a strength: cheaper, predictable, and easy to test.
When it fitsThe steps are known and always happen in the same order. If some requests need different steps, you want a supervisor's routing instead.

The price, part 1What a team costs

Class 5.7 (Assemble a single agent) summed cost over one agent's steps. A team adds a second sum, over agents:

$$C_{team} \;=\; \sum_{a=1}^{A}\;\sum_{s=1}^{n_a}\bigl(t^{in}_{a,s}\,p_{in} \;+\; t^{out}_{a,s}\,p_{out}\bigr)$$

Every symbol\(A\) is the number of agents, the supervisor included. \(n_a\) is how many model calls agent \(a\) makes. \(t^{in}_{a,s}\) and \(t^{out}_{a,s}\) are the input and output tokens of agent \(a\) on call \(s\). \(p_{in}\) and \(p_{out}\) are the prices per token.
What it saysThe supervisor is not free: it pays a call at every hop, on top of each worker's own calls. The build measures this sum per agent, so you see exactly where the tokens go.

The price, part 2Failure compounds

In a chain of agents, the whole run succeeds only if every stage does. If each of \(k\) stages succeeds independently with probability \(p\):

$$P(\text{run succeeds}) \;=\; p^{\,k}$$

Worked exampleFive stages that each succeed 95% of the time: \(0.95^5 \approx 0.77\). At 90% each: \(0.9^5 \approx 0.59\). A team of individually good agents can be a mediocre system.
An honest caveatReal stages are not independent, and a reviewer can catch an earlier mistake. Treat the formula as an idealization; the lesson is that reliability decays multiplicatively, so every added stage must earn its place.
