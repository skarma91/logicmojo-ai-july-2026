The goalAnswers grounded in your documents

The two properties that matterThe answer is grounded (it comes from your documents, not the model's memory) and attributable (you can check each claim against a cited source). Together they make it trustworthy.

Why RAGIt fixes the two big LLM weaknesses

Weakness 1: no private knowledge

The model never saw your handbook or tickets. On its own it cannot answer questions about them.

RAG: retrieves the relevant passages and puts them in the prompt, so the model reads them at question time.

Weakness 2: confident hallucination

Asked something it does not know, the model often invents a fluent, wrong answer.

RAG: grounds the answer in real text and cites it, so made-up claims are far less likely and easy to catch.

The one-line ideaRetrieval-augmented generation = find the relevant text first, then ask the model to answer using that text.

The loopSix steps, split into build time and query time

Query timeRetrieve, augment, generate

The instruction does the grounding"Use only the context" is what keeps the model from wandering into its own memory. Retrieval supplies the facts; the instruction forces the model to stay inside them.

CitationsCarry the source through the whole loop

Each chunk carries its source metadata from ingestion onward. When you build the prompt, number the chunks and label each with its source. Ask the model to cite those numbers, then map the numbers back to real sources for the reader.

Why it is non-negotiableA grounded answer you cannot verify is just a confident answer. Citations let a reader check the claim, and let you debug which retrieved passage led the model astray.

MisconceptionRAG does not retrain the model

"RAG teaches the model my documents." It does not. The model's weights never change. RAG simply places relevant text in the prompt at question time; the model reads its context, as always, and answers.

ConsequenceUpdate a document and the next answer reflects it immediately, no retraining. This is exactly why RAG, not fine-tuning, is the right tool for knowledge (a point we return to in class 4.9, Fine-tuning I).

The buildHand-build the loop, then break it on purpose

Assemble the full loop over the real IRS corpus from class 4.4: retrieve, build a cited prompt, generate. Then trigger a stale-document failure and fix it live, so you feel that retrieval quality decides answer quality.

  • Reuse the FAISS retriever from class 4.4 (Embeddings and vector databases).
  • Build a prompt that carries numbered context, cited by publication, tax year, and page.
  • Ask "what is the standard deduction for a single filer"; without a filter last year's passage is retrieved and the answer quotes the old figure.
  • Fix it with a tax_year metadata filter; the answer corrects to the current figure.

See itA small UI that makes retrieval visible

The loop is the same functions you just wrote; a thin Streamlit app puts a face on it. A text box takes the question, the app runs retrieve then augment then generate, and shows the grounded answer with its sources.

The point of the app is the panel below the answer: show the retrieved chunks and their similarity scores. Now the bad-chunk failure is not a story, it is on screen. When an answer looks wrong, you open the panel and see which passage misled it.

Why a UI hereStreamlit returned from class 4.1 (Working with LLMs). Reuse: the logic lives in main.py; app.py only imports answer() and draws the boxes. No new RAG code.

Looking aheadThe RAG landscape: you built the naive one

Everything you just built is naive RAG: retrieve once, augment, generate. It is the base every other variant improves on. Each upgrade below sharpens one of the same six steps; none of them replaces the loop.
