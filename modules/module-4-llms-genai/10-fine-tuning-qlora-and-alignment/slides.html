Run itLaunching the QLoRA job

The dataset and config from class 4.9 are ready. Launching training is one call: the trainer runs the class 2.2 (How models learn) loop, forward, loss, backpropagate, update, but only on the small LoRA add-on, while the 4-bit base stays frozen.

What actually trainsThe base model is quantized to 4-bit and frozen; gradients flow only into the LoRA matrices \(B\) and \(A\). That is why a run that would need a large GPU at full precision fits a free Colab GPU.
What to expectLoss drops over a few epochs as the model adopts the house style. It is fast because the trained part is tiny, but not instant, which is the next slide's problem.

The patternPre-baking: do not wait on the clock

Even a small QLoRA run takes longer than a class can wait watching a progress bar. The fix is the pre-bake pattern: a finished checkpoint is prepared ahead of time, so you kick off the live run to see it start, then switch to the pre-baked checkpoint to evaluate, merge, and serve without waiting.

A general habitAny slow step, a long training run, a big embedding job, a data download, is better pre-baked for a live session. Start the real thing, then work against a ready artifact.
To be clearThis is a convenience for live sessions and demos, not a production training practice. In real work you run the job to completion and use its checkpoint; reusing an already-trained checkpoint is normal, abandoning a run for a pre-made one is only to save class time.

Did it help?Evaluate tuned versus base

A fine-tune is only worth shipping if it measurably beats the base model. Run both on held-out questions and on the class 4.8 eval set, and compare: did the target behavior (the house style) improve, and did general ability hold?

Two things to checkNot just "is the behavior better", but also "did I break anything else". A fine-tune can nail the style yet get worse at everything outside the training distribution. Measure both.

The riskWatch for overfitting

A small dataset trained for too long makes the model memorize the examples instead of learning the pattern (overfitting, from class 2.1). It parrots training answers and gets worse on anything new.

The signsTraining loss keeps falling while validation loss turns back up; the model repeats training phrasings verbatim; and its answers to unrelated prompts degrade.
The fixesFewer epochs, more and more varied data, a smaller LoRA rank, and early stopping when validation loss rises. Always judge on held-out data, never on what it trained on.

Ship itMerge and serve

Training leaves you with a frozen base plus a separate LoRA add-on. Merging folds the add-on back into the weights, computing \(W' = W + BA\) once, to give a single standalone model you can serve like any other, through Ollama or an API endpoint.

Merge or keep separateMerged is simplest to deploy: one model, no adapter to load. Keeping the adapter separate is lighter to store and lets you swap behaviors on one base. Merge when you will serve just this one.
What precision comes outThe LoRA add-on is 16-bit and is never quantized. If you keep it separate, the base stays 4-bit and does the same dequantize-then-matmul at inference, with the adapter's small 16-bit term added on top. If you merge, the 4-bit base must be dequantized to add \(BA\), so the merged model is a full 16-bit model, not 4-bit. To ship a small artifact, re-quantize it afterward (for example export to 4-bit GGUF for Ollama).

AlignmentFrom raw model to helpful assistant

Pretraining gives a model raw next-token ability; it can continue text but not reliably follow instructions. Alignment is the stage that shapes it to be helpful and do what you ask. At intuition level it is a pipeline.

Preference optimizationDPO: learn from preferred vs rejected

DPO (Direct Preference Optimization) is the practical modern method. You give it pairs where one answer is preferred and one is rejected, and it adjusts the model so the preferred answer becomes more likely than the rejected one.

The idea in one linePush up the probability of the chosen answer and down the probability of the rejected one: make \( p(\text{preferred}) > p(\text{rejected}) \), measured against a frozen reference copy of the model. No separate reward model or reinforcement loop, which is why it is the common default now.
Where the pairs come fromPreferences are gathered offline into a fixed dataset of (prompt, chosen, rejected), then trained in one pass. The labels come from human raters, or from an AI judge, which is RLAIF (RL from AI feedback; Anthropic's Constitutional AI is the known example). The DPO pass itself can use LoRA.
You have probably seen thisWhen a chat app shows two answers and asks "which do you prefer?", that is exactly this: two samples for one prompt, and your click labels the pair (chosen vs rejected). It is not applied live; the votes are pooled and fed into a later training run.

The ancestorPPO with RLHF

RLHF (Reinforcement Learning from Human Feedback) with PPO (Proximal Policy Optimization) was the earlier approach that made models like the first ChatGPT follow instructions. It trains a separate reward model from human comparisons, then uses reinforcement learning to push the model toward higher-reward answers.

Why we name it but do not build itIt works, but it is complex: a reward model, an RL loop, and careful tuning to stay stable. DPO largely reaches the same goal more simply, so PPO-RLHF is best understood as the ancestor that DPO streamlined.

For reasoningRLVR and GRPO

RLVR: a reward source

Reinforcement learning from verifiable rewards. It only applies where the training prompts have ground truth, a math answer key or a test suite for code. A deterministic verifier replaces the human or reward model and returns pass or fail.

GRPO: an algorithm

Group Relative Policy Optimization. A PPO variant with no separate value network: sample a group of answers per prompt, score each, and push toward those above the group's average. Efficient, and used to train many recent reasoning models.

Not the same axisRLVR is where the reward comes from; GRPO is the optimizer. GRPO is not a subset of RLVR: they are usually paired (verifiable reward + GRPO, as in recent reasoning models), but each can exist without the other.
How "checked automatically" worksA program scores the output and that score is the reward: math (compare the final answer to the known one), code (run unit tests, does it compile), format (regex or JSON-schema validation), puzzles (a rules engine). No human in the loop.

MisconceptionAlignment is not just censorship

"Alignment means the model refuses things." Refusals are one small part. At its core, alignment is what turns a raw text predictor into something that follows your instructions, stays on task, and answers helpfully. Safety is one slice of a much broader helpfulness goal.

Put plainlyWithout alignment, a pretrained model rambles and ignores what you asked. The SFT you ran today, and the preference methods above, are what make a model usable at all, not merely what makes it decline.
