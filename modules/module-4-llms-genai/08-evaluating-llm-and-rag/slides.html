Evaluating LLM and RAG systems

The frameProving it works is the hard part

A demo that answers one question well proves nothing. A real system has to be right across many questions, and it can fail in quiet, specific ways: a fluent answer that is subtly wrong, a correct answer built on the wrong passage, or an answer that dodges the question.

It can hallucinate

Say something confident that the retrieved context does not support.

It can miss the point

Answer fluently but not actually address what was asked.

Retrieval can fail

Fetch the wrong passages, so even a good model has nothing to work with.

The goal todayTurn "it seems good" into numbers you trust, so a change is judged by evidence, not by vibes.

The problemWhy language eval is hard

A multiple-choice test has one right answer, so scoring is trivial. A written answer does not: two very different sentences can both be correct, and one fluent paragraph can be completely wrong. Plain accuracy cannot capture that.

The analogyEvaluating an LLM is like grading an essay, not marking a multiple-choice test. You need a rubric with several dimensions, not a single tick or cross.

The metricsThree questions, four numbers

Instead of one score, measure a RAG answer along the axes that can each fail on their own. Each metric isolates a different failure, so a low one tells you where to look.

Generator versus retrieverFaithfulness and answer relevance grade the answer; context relevance and recall grade the retriever. Splitting them tells you whether to fix the prompt and model, or the search.

Metric 1Faithfulness: is every claim supported?

Break the answer into individual factual claims, then check each one against the retrieved context. Faithfulness is the fraction that the context actually supports.

$$ \text{faithfulness} = \frac{\text{supported claims}}{\text{total claims}} $$

Reading itA score of 1 means every statement is grounded. Below 1 means the answer asserted something the passages do not back, the signature of hallucination. It does not ask whether the answer is useful, only whether it is grounded.

Metric 2Answer relevance: does it address the question?

A grounded answer can still miss the point: correct, but not what was asked. Answer relevance scores how directly the reply responds to the question, on a rubric from 0 to 1.

Faithful is not the same as relevant"The HSA limit is 4,300" is perfectly faithful, but if the question was about the standard deduction it scores low on relevance. The two metrics catch different faults, which is why you need both.

Metric 3 and 4Grading the retriever: relevance and recall

Context relevance (precision)

Of the passages retrieval returned, how many are actually about the question. Noise crowds the prompt and can mislead the model.

\( \dfrac{\text{relevant retrieved}}{\text{retrieved}} \)

Context recall

Did retrieval fetch the passage that truly holds the answer (the labeled gold passage)? If it did not, no model can answer well.

\( \dfrac{\text{gold passages retrieved}}{\text{gold passages}} \)

Why recall is the cheap oneRecall needs no judge: you labeled the gold passage when you built the eval set, so it is a deterministic check, the same idea as hit@k from class 4.6 (RAG with frameworks). Relevance needs a judgment call, so it uses the model as judge (next).

MisconceptionOne score is not enough

"Give me one number for quality." There is no honest single number. A fluent answer can be unfaithful; perfect retrieval can still be answered off-topic. Collapse the metrics into one and you hide exactly the failure you needed to see.

Read them togetherLow faithfulness but high recall means the model is ignoring good context: fix the prompt. High faithfulness but low recall means the search missed: fix the retriever. The pattern across metrics is the diagnosis.

DecidingCombining metrics: gates, weights, and what matters when

Keep the metrics separate to diagnose. Combine them only to make a decision (ship or not, which system wins), and do it deliberately in two layers, not with a blind average.

Hard gates first

Non-negotiable minimums. A hallucination is not offset by fluent relevance, so faithfulness (and any safety metric) must clear a threshold, for example \( \ge 0.95 \), or the whole answer fails regardless of the rest.

Then a weighted average

For the metrics where trade-offs are fair, combine into one number: \( \text{score} = \sum_i w_i\, m_i \), with \( \sum_i w_i = 1 \). Here \(m_i\) is each metric (on 0 to 1) and \(w_i\) its weight. Use this for a leaderboard or a go/no-go, never as the only thing you look at.

When your use case is...
Weight most (often a gate)
High-stakes factual (medical, legal, finance)
faithfulness and safety: a wrong answer is costly, so gate these.
Large corpus, needle in a haystack
context recall: if the right passage is missed, nothing downstream helps.
Tight context window or a small model

Chat and helpfulness

exact match and schema validity: relevance barely applies.
Setting the weightsWeight by the business cost of each error type, then check the composite ranks systems the way a human would on a small labeled sample. Keep the per-metric dashboard alongside; the composite is for the decision, the breakdown is for the fix.

The toolLLM as judge, and its biases

Faithfulness and relevance need a judgment a human would make, but by hand that does not scale. So we use a capable model as the judge: give it the question, the answer, the context, and a clear rubric, and have it return a short reason then a score. Fast and useful, but it brings its own biases, so know them before you trust the number.

Bias
What it does
Verbosity
rates longer, wordier answers higher regardless of correctness.
Position
in an A vs B comparison, favors whichever answer is shown first.
Self-preference
rates its own outputs, and its own family's style, higher than others.
Leniency and drift
tends to be too generous, and can score the same answer differently run to run.

The toolGuarding the judge: mitigations

Each bias has a concrete countermeasure. None makes the judge perfect; together they make it trustworthy enough to act on.

Do this
Because it fixes
Score against a rubric, reason first
a fixed rubric and a short justification before the number curb verbosity and make scores consistent, not vibes.
Randomize order, or score absolutely
removes position bias: shuffle A and B, or grade each answer on its own 0-to-1 scale instead of comparing two.
Judge with a different, stronger model
fixes self-preference: do not let the model that wrote the answer be the only grader of its own work; a separate or stronger judge, or a panel, is fairer.
Low temperature, average repeats
reduces run-to-run drift so the same answer gets close to the same score.
Calibrate against human labels
hand-label a small sample and check the judge agrees; trust it only as far as it tracks people.
The one rule that matters mostThe judge is a proxy for a human. Its scores are only worth acting on to the extent they agree with a small set of human-labeled examples, so measure that agreement, do not assume it.

The assetBuilding a representative eval set

Metrics need something to run on. An eval set is a fixed list of items, each a question, a reference answer, and the gold passage that holds it, chosen to reflect the questions real users actually ask (common cases, edge cases, and things the corpus does not cover, so you can check it says "not found").

What makes it representativeCover the real distribution: the frequent questions, the tricky ones, the year-sensitive ones, and a few unanswerable ones. Thirty good items beat three hundred careless ones.
Why it is an assetBuild it once and reuse it forever: every time you change the retriever (4.6), the model, or add a fine-tune (4.10), you rerun the same set and see if the numbers moved. It is your regression test.

The standard libraryRAGAS, and why we hand-build first

RAGAS is the widely used open library for exactly these RAG metrics: faithfulness, answer relevance, context precision, and context recall, computed with an LLM judge and embeddings. Worth knowing by name, and reaching for once you understand what it measures.

Why we hand-build them hereWriting each metric as a small LLM-as-judge call (about 40 lines) makes the definitions concrete: you see exactly what "faithfulness" checks. A library that prints a number you cannot explain teaches nothing.
Using RAGAS for realInstall: pip install ragas datasets, and configure a judge model and an embeddings model. Then wrap your (question, answer, contexts, ground_truth) rows in its dataset format and call its metrics.
The pitfall to expectRAGAS pins specific LangChain and related versions, which often clash with a current LangChain or LangGraph install. Budget time for a dependency conflict, or run it in an isolated environment. This is why our build keeps RAGAS as a reference block, not the core.

DiagnosisReading the scores: which failure, which fix

The point of separate metrics is the pattern they make. Each pattern points at a different part of the pipeline, so the scores tell you what to fix, not just that something is wrong.

The split that guides youRecall and precision point at the retriever; faithfulness and answer relevance point at the prompt and model. Which pair is low tells you which half of the system to touch.
