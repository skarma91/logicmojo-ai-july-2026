Prompt engineering for production

A clever prompt that works once is a demo. A prompt you can trust, test, version, and defend is a product. This is the move from one to the other.

The shiftA demo prompt is not a production prompt

A prompt is the full text you send the model: the system instructions, the user's request, and any examples or context. Prompt engineering is writing that text so the model does the right thing reliably.

In a demo you adjust the prompt until it works on the one input you are showing. In production the same prompt meets thousands of inputs you never saw, and "I will just reword it" does not scale.

Production prompting is a small set of durable techniques: give examples, break work down, reason only when it helps, and keep prompts as versioned, testable artifacts.

Few-shotShow the pattern, do not just describe it

The simplest prompt is zero-shot: instructions and the input, but no examples. It often works, yet on tasks with a strict format it drifts. Few-shot fixes that by putting a few input-output examples directly in the prompt, so the model copies the pattern it sees. It is the cheapest reliability upgrade you have, no training required.

Task for this classIn a support inbox, every incoming message becomes a ticket, and its ticket title is the one-line summary an agent scans in the queue. We will auto-generate that title from the message: Title Case, at most six words, no ending punctuation. Easy to state, easy to get subtly wrong.
Zero-shot: instructions, no examplesSystem: "Write a short ticket title for this message." User: "I was charged twice and want a refund." Model: "Sure! Here is a concise title: Customer Reports Being Charged Twice and Requests a Refund." Too long, wrong style, chatty preamble.

Few-shotTwo examples fix it

zero-shot

in: "I was charged twice and want a refund."

out: "Sure! Here is a concise title: Customer Reports Being Charged Twice and Requests a Refund."

two-shot

example 1: "the app keeps crashing" -> "App Crash On Launch"

example 2: "how do I add a user" -> "How To Add A User"

in: "I was charged twice and want a refund."

out: "Charged Twice, Refund Requested"

Why it worksThe examples pin the exact format and length. The model no longer guesses what "short title" means; it matches the shape you showed. Two or three good examples usually beat a paragraph of instructions.

DecompositionBreak a hard task into prompted steps

One prompt asked to do five things at once does each poorly. Split the task into steps, prompt each, and pass results forward. Each step is simpler, more reliable, and easier to debug.

Chain-of-thoughtReasoning helps on multi-step problems

Asking the model to work step by step before answering genuinely improves multi-step problems: arithmetic, logic, anything with intermediate results. It gives the model room to compute instead of guessing in one leap.

Problem: "$12 per user per month. A team runs 3 users for 4 months, then 2 more users join for a 5th month. What is the total?"

direct answer

out: "$168"

Wrong. It counted the 3 users for 4 months ($144) and only the 2 new users in month 5 ($24), forgetting the original 3 are still active.

step by step

"Months 1 to 4: 3 users x $12 x 4 = $144.
Month 5: now 3 + 2 = 5 users x $12 = $60.
Total = 144 + 60."

out: "$204" (correct)

Why it helpsWriting month 5 out as its own step forces the model to recount the active users (5, not 2). The direct answer skipped that and silently dropped the original three.

Chain-of-thoughtOn easy tasks it just costs more

Adding "let us think step by step" to every prompt should not be automatic. On a simple lookup or classification, reasoning adds tokens, latency, and cost while changing nothing about the answer.

Judgment, not a ruleUse chain-of-thought when the task has real intermediate steps. Skip it when the answer is a direct recall or a one-step label.

TemplatingPrompts are code, not buried strings

A prompt glued together with f-strings deep inside a function is invisible and unchangeable. Pull it out into a named template with explicit variables, so you can read it, edit it, and reuse it.

buried in code
resp = call(f"Summarize this "
  f"in 2 lines: {text} "
  f"tone: {tone}")

Hard to find, hard to change, impossible to compare.

a named template
SUMMARY_V1 = (
  "Summarize the text in 2 lines.\n"
  "Tone: {tone}\n\nText:\n{text}")
resp = call(SUMMARY_V1.format(
  tone=tone, text=text))

One place to read and edit; variables are explicit.

VersioningGive prompts versions, because they drift

Give each prompt a name and a version, and never overwrite it in place. The reason is drift: a prompt's quality changes over time even when you do not touch it, and you want that change measured, not silent.

What makes a prompt driftThe provider updates the model behind it, a teammate edits the wording, or the mix of real inputs shifts. Any one of these can turn yesterday's good prompt into today's mediocre one.
What a "score" isAn objective pass rate on a fixed check. For the ticket titles: is it Title Case, six words or fewer, no trailing punctuation? A prompt whose output passes 9 of 10 inputs scores 9/10.

Prompt injectionText in the prompt can fight your instructions

Your prompt often contains text you do not control: a user message, or a document you retrieved. That text can carry instructions aimed at the model, trying to override yours. This is prompt injection.

Prompt injectionThe system prompt is not untouchable

It is tempting to assume the system prompt always wins. It does not. To the model it is all just text, and a well-placed injected instruction can override yours.

No single instruction fixes this. You design for it: separate instructions from untrusted content, constrain outputs, and validate. The full defenses come in Module 6 (AI security).

Recognize the risk now
  • Any user or document text is untrusted input.
  • "Ignore previous instructions" is the classic tell, but attacks get subtler.
  • Treat the model's output as untrusted too, especially before it triggers an action.
The defenses, named (Module 6, class 6.5, AI security)These are concrete, not vague: fence and label untrusted text, filter inputs and outputs, least-privilege on any tool the model can call, and a human approval step before risky actions.

The buildRun an A/B test of two prompts

What an A/B test isCompare two variants, A and B, on the same inputs and keep the better one. This is an offline test: a fixed set of ten inputs and an automatic scorer, run before shipping. Testing on live user traffic instead would be an online A/B test.

Slide 10 gave the principle (version prompts, watch for drift, score them). Here you build the comparison: V1 plain versus V2 with two few-shot examples and a length rule, scored on the same ten messages.

  • Prompts as named templates, V1 and V2.
  • A fixed list of ten input messages.
  • The scorer from slide 10: Title Case, six words or fewer, no trailing punctuation.
  • Report each score and the winner.
Ten is a teaching sizeReal prompt evaluation scores against a larger, representative eval set, tens to hundreds of examples that mirror production traffic. Building and using one is class 4.8 (Evaluating LLM and RAG systems).

WrapWhat you can do now, and what is next

You can now
  • Add few-shot examples to pin format and behavior.
  • Decompose a hard task into checkable steps.
  • Use chain-of-thought where it helps and skip it where it does not.
  • Keep prompts as versioned templates and A/B test them.
  • Recognize prompt injection when you see it.
Micro-assignment

Run an A/B test of two prompt variants over ten inputs, score both, and report which won and why.
