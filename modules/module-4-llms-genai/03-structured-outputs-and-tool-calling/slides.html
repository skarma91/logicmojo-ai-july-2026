Structured outputs and tool calling

A paragraph is for a person. A program needs data it can trust and functions the model can call. This is the substrate every agent stands on.

The shiftFree text is for humans, JSON is for code

A friendly paragraph is perfect for a reader and useless to a program. If the next step is code (store it, route it, act on it), the model must return a fixed, parseable shape.

Two tools do this: structured output (JSON validated against a schema) and tool calling (the model requests one of your functions with typed arguments).

JSON modeAsk for strict JSON, get parseable data

Most providers offer a JSON mode: you request JSON, and the model constrains its output to valid JSON syntax. That removes the chatty preamble and trailing prose that break json.loads.

plain request

"Extract product and quantity."

"Sure, they want 3 seats: {...}" → json.loads fails on the preamble

JSON mode on

"Extract product and quantity. Respond as JSON."

{"product":"seats","quantity":3} → parses cleanly

Necessary, not sufficientJSON mode guarantees valid JSON syntax. It does not guarantee the right fields or types. For that you need a schema, next.
In practiceHow you request JSON differs by provider (a flag, a response-format argument, or just the prompt), and local models may not enforce it at all. The validation step you build next is provider-agnostic, so it protects you no matter how the JSON was produced.

The contractA Pydantic model declares the shape

Define exactly what you expect as a Pydantic model. This is the type-hints habit from class 1.2 (Python core), now enforced at runtime: the model's JSON must match, or you find out immediately.

from pydantic import BaseModel
from typing import Literal

class Order(BaseModel):
    product: str
    quantity: int
    priority: Literal["low", "normal", "high"]   # only these three allowed
What this buys youThree guarantees in one place: the fields that must exist, their types, and the allowed values. The schema is the single source of truth for what "a valid order" means.

ValidationA good response passes cleanly

Feed the model's JSON to the schema. If it fits, you get back a typed Python object with real attributes, not a raw dict you have to second-guess.

After this lineorder.quantity is guaranteed to be an int, and order.priority is one of the three allowed strings. Downstream code can trust it.
raw = '{"product": "seats", "quantity": 3, "priority": "high"}'

order = Order.model_validate_json(raw)
print(order.product)     # seats
print(order.quantity)    # 3  (an int, not "3")
print(order.priority)    # high

ValidationA bad response raises a clear error

bad = '{"product": "seats", "quantity": "three", "priority": "high"}'

try:
    Order.model_validate_json(bad)
except ValidationError as e:
    print(e)
# quantity: Input should be a valid integer,
#   unable to parse string as an integer

Here quantity came back as the word "three". Without a schema that flows downstream and crashes something far away. With one, it fails right here, with a message that names the field and the problem.

The pointFail early, fail loud, fail where you can see it. Validation turns a silent, distant bug into an obvious local one.

ReliabilityIt does not always return valid JSON

"The model always returns valid JSON" is false. It sometimes adds a stray comment, drops a field, or mistypes a value. The reliable pattern is validate, and on failure, retry with the error fed back.

Cap the retriesTwo or three attempts, then give up and report. A retry loop without a cap is a runaway cost waiting to happen (a failure mode we harden in Module 5).

Tool callingThe model asks to run a function

A model cannot look up a live invoice or send an email on its own. Tool calling is how it asks: instead of answering, it emits a structured request to call one of the functions you offered, with arguments filled in.

Your code runs the function and hands the result back. The model never runs anything itself; it only requests, and you stay in control of what actually executes.

The key inversion

Normal call: prompt in, text out.

Tool call: prompt in, a request to run a function out, which your code fulfills and feeds back.

Tool callingDescribe a tool as a schema

You tell the model what tools exist by describing each one: a name, a plain-language description of when to use it, and a typed parameter schema. Same idea as the Pydantic contract, now for a function's inputs.

{
  "name": "get_invoice_status",
  "description": "Look up the current status of an invoice by its id.",
  "parameters": {
    "type": "object",
    "properties": { "invoice_id": { "type": "string" } },
    "required": ["invoice_id"]
  }
}
The description is not decorationThe model chooses a tool from these descriptions. A vague one gets called at the wrong time; a precise one gets called correctly. Write them like documentation.
Tools cost tokens tooEvery tool's name, description, and parameter schema is sent with the prompt on each call, so it counts against the token budget and the cost (class 4.1, Working with LLMs). A few well-chosen tools keep prompts lean; offering dozens of rarely-used tools inflates every request and can exhaust the context window quickly.

Tool callingThe three-step round trip

Read itThe model requests, your code executes and returns, the model writes the final answer using the result. That round trip, run in a loop, is an agent.

Why it mattersThis is the agent loop, in miniature

An agent is nothing more than this round trip, repeated: the model looks at the goal and the tools, requests one, sees the result, and decides the next request until it can answer.
