The frameworkWhat LangChain is, and why use one

LangChain is an open-source framework for building applications on top of LLMs. It ships ready-made, swappable components (model wrappers, prompt templates, retrievers, output parsers) and a standard way to connect them, so you stop hand-writing the plumbing you wrote in class 4.5 (RAG from scratch).

LCEL and the pipe

LCEL is the LangChain Expression Language. Every component is a runnable with the same interface, so you connect them with the pipe |, read left to right: each step's output becomes the next step's input, like a Unix pipe.

Why a framework, and the catch

You can swap a retriever or model without rewiring, and common patterns come for free. The catch: it is opinionated and hides detail, which is exactly why we built the loop by hand first. LangChain is the most common choice; LlamaIndex and plain Python are valid alternatives.

Why we also switch FAISS to ChromaFAISS (classes 4.4 and 4.5) is a vector index: it stores only vectors, so we kept the text and metadata in a parallel list and filtered by hand after over-fetching (the "retrieve a wider pool, then keep the current year" step). Chroma is a vector database: it stores vectors, text, and metadata together, filters on metadata natively inside the query (no hand-rolled loop), persists to disk, and has a first-class LangChain integration that drops into a retriever. It is free and runs embedded (no server), and it uses an HNSW index by default (class 4.4, Embeddings and vector databases) for fast approximate search. It removes exactly the plumbing we wrote by hand. FAISS is still fine for a fast in-memory index; Qdrant, Weaviate, or pgvector are the step up when you need a networked or managed store.

Upgrade 1Query rewriting: fix the question first

Users ask vague, underspecified questions. A short pre-step rewrites the query into something retrieval can match, before it ever hits the index.

Two rewrites1. "it broke after the update" to "reports show wrong totals after the latest software update". 2. "can I deduct my home office" to "home office deduction eligibility and how it is calculated for the self-employed". Both now carry the terms a document search can match.
It costs an extra callThe rewrite is itself an LLM call that runs before every retrieval, so each query makes one more model call: more latency and more cost. Worth it when questions are vague; skip it when they already carry the right terms.

Upgrade 2Re-ranking: retrieve broadly, then rank carefully

Vector search is fast but approximate. Two-stage retrieval fixes that: first retrieve a broad set cheaply, then re-score those few candidates with a slower, more accurate cross-encoder and keep the best.

Why two stagesA cross-encoder is too slow to score every chunk in the corpus, but perfect for re-scoring the 20 the fast search already narrowed to. Cheap filter, then expensive judge.

Under the hoodInside the cross-encoder

Why the split worksThe bi-encoder is cheap enough to search the whole corpus but cannot see the two texts together; the cross-encoder sees them together and scores precisely but is too slow for the whole corpus. Two-stage retrieval uses each where it is strong: bi-encoder to shortlist, cross-encoder to rank.

Under the hoodCross-encoder: how it is trained and used

The pair is fed as one sequence, [CLS] query [SEP] passage [SEP]: [SEP] marks the boundary, and [CLS] is a special token with no word meaning: because attention lets it read every query and passage token, training teaches the model to use its final vector as the pair's summary. A linear head maps that vector to one relevance score.

How it is trainedStart from a pretrained encoder (BERT, MiniLM) and add the linear head. Fine-tune on labeled (query, passage) pairs from MS MARCO: passages that answer the query are positives, and hard negatives (mined with a first-stage retriever) are the rest. The loss rewards a high score for a true match, so the head learns relevance.
How it re-ranks (inference)The fast first stage, the bi-encoder dense search from the previous slide (or BM25), narrows to a shortlist (say 20). Run one forward pass per (query, passage) pair to score each, then sort and keep the top k. The score needs both texts together, so passages cannot be pre-encoded: accurate, but too slow for the whole corpus, which is why it only re-ranks a shortlist.

Further upgradesNamed, so you know they exist

Parent-document retrieval

Search over small, precise chunks, but hand the model the larger parent section they came from, so it gets both a sharp match and enough surrounding context.

Contextual retrieval

Before embedding, prepend a short description of where each chunk sits in its document. The chunk becomes self-describing, so retrieval matches it more reliably.

The pattern behind all of themEvery upgrade so far improves what you retrieve. That is worth a lot, and it has a ceiling, which is the next slide.

Advanced architectureHyDE: search with a hypothetical answer

A short question and the passage that answers it often use different words, so their embeddings sit far apart. HyDE (Hypothetical Document Embeddings) closes that gap.

Ask the model to draft a hypothetical answer to the question. It may contain errors; that does not matter. Embed that draft and retrieve the real passages nearest to it. The draft reads like the target documents, so it lands in the right neighborhood.

The costTwo LLM calls per query, one to draft and one to answer, plus retrieval. It runs at query time, so it adds latency to every question.

Advanced architectureHyPE: match question to question

HyPE (Hypothetical Prompt Embeddings) flips HyDE: do the generating once, at indexing time, not on every query.

For each chunk, ask the model to write a few questions that chunk would answer. Embed those questions and store them pointing back to the chunk. At query time the user's real question matches a stored question, question to question, and returns its chunk.

The trade-offThe cost moves offline: query time is a plain retrieve, no extra call. In return the index grows, several question vectors per chunk, and indexing does more work up front.

The wider mapFour more RAG architectures, in one line each

Beyond query-side tricks, these reshape retrieval itself. Named here so you can recognize and reach for them; the deeper study is in this module's suggested reading.

Architecture
What it adds
RAG-fusion
Run several variants of the query, retrieve for each, then merge the rankings (reciprocal rank fusion) into one stronger list.
Corrective RAG (CRAG)
Grade the retrieved passages first; if they look weak, re-search or fall back before generating, instead of answering from bad context.
GraphRAG
Build a knowledge graph of entities and relations from the corpus, then retrieve over the graph for multi-hop and whole-corpus questions.
Agentic RAG
The model decides when and what to retrieve, and can loop and call other tools. This is the bridge to Module 5 (AI Agents).
How to hold thisQuery-side (rewrite, HyDE, HyPE) improves the question; structure-side (fusion, CRAG, GraphRAG) improves retrieval; agentic hands control to the model. Reach for one only when a real failure calls for it.

The honest limitWhere RAG breaks

RAG answers questions from documents. It cannot take an action, call a tool, or run a multi-step task. Some requests are not retrieval problems at all, and no amount of better retrieval will solve them.

Misconception"Better retrieval fixes everything." It does not. "Issue the refund and email the customer" needs the system to act, not just to find a passage.
Where agents beginActing on a request, calling tools, and running several steps is exactly what an agent does. That is Module 5 (AI Agents), where this retriever becomes the agent's first tool.
