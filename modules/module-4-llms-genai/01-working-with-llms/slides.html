The interfaceA chat model reads a list of messages

A prompt is everything you send the model for one turn. A chat model is not a new kind of network: it is a base model that was instruction-tuned and aligned (the three stages from class 3.5, From models to LLMs), which is what makes it follow roles and answer instead of just continuing text. It takes an ordered list of messages, each tagged with a role, and writes the next assistant turn.

The whole list is the inputEach call resends the full conversation. The model keeps no state between calls, so the message list is its only memory. Agents rely on this heavily (Module 5, AI agents).

Why replay the assistant turnsSince the model is stateless, prior assistant messages are how it "remembers" its own earlier answers in a multi-turn chat. Leave them out and it loses the thread.

The system promptSame question, two system prompts

The system prompt is the strongest control you have. Hold the user message fixed, change only the system prompt, and the answer changes shape completely.

system A

"You are a terse expert. One sentence, no pleasantries."

user (same)

"Explain what an invoice is."

Reply: "A bill a seller issues to a buyer listing goods, amounts, and payment terms."

system B

"You are a friendly tutor for absolute beginners. Use an everyday analogy."

user (same)

"Explain what an invoice is."

Reply: "Think of a restaurant check: it lists what you ordered and what you owe. An invoice is that check, for a business sale."

Misconception, corrected"The system prompt is decoration." It is not. It shapes tone, format, and behavior on every turn, and it is where you set the rules of the task.

Two knobsTemperature and streaming

Temperature (from class 3.5, decoding) sets randomness. Low is focused and repeatable; high is varied and creative. Set it per task: near 0 for extraction, higher for brainstorming.

Streaming returns tokens as they are generated instead of waiting for the whole answer. Same result, but the user sees words appear immediately, which feels far more responsive.

Temperature, concretelyPrompt: "Name a budgeting app." At \( T = 0.2 \) you get the same safe pick almost every run ("BudgetWise"). At \( T = 1.0 \) it varies run to run ("PennyPilot", "CashCompass", "MintLedger"). Same model, same prompt, different randomness.

CostYou pay per token, both directions

Providers bill by the token, and they charge separately for what you send and what you get back:

$$ \text{cost} \;=\; \underbrace{n_{\text{in}} \cdot p_{\text{in}}}_{\text{your prompt}} \;+\; \underbrace{n_{\text{out}} \cdot p_{\text{out}}}_{\text{the answer}} $$

Symbol
In plain words
\( n_{\text{in}} \)
number of input tokens: the system prompt plus the whole message list you send.
\( n_{\text{out}} \)
number of output tokens the model generates in its reply.
\( p_{\text{in}}, p_{\text{out}} \)
the price per token for input and for output. Output usually costs more than input.
Read it aloud"Pay for every token I send, plus every token it writes back." This is why a long system prompt resent on every turn quietly increases the cost, and why the context window is a budget.

How "this call" is computedPlug the token counts into the formula. Frontier: \( \frac{1500}{10^6} \times 2.50 + \frac{500}{10^6} \times 10.00 = 0.00375 + 0.005 = \$0.00875 \), rounded to about $0.009. The other rows use the same arithmetic with their prices.
The gap is realThe frontier call here costs roughly 90 times the hosted-open one, and the local call is free. At one request that is nothing. At a million requests a day it decides whether your product is viable.

Where it runsThree ways to run an LLM

The realityWhat that table leaves out

The three tiers are a starting frame, not the full decision. In a real organization, cost is only one axis among several.

Vendor relationships often decide itMany companies standardize on one frontier vendor (OpenAI or Anthropic) under a contract or partnership, and use it everywhere for consistency, support, security review, and compliance, even when a cheaper model would do. Procurement and data agreements can matter more than the per-token price.
Local is for building, not shippingRunning on your laptop is perfect for development and experiments, but it is not a product. A real product must be hosted so it is always on, reachable, and able to serve many users at once.
Self-hosting is its own job"Open weights" is not "free to serve." Hosting an open model yourself means GPUs or a serving platform, autoscaling, latency budgets, uptime, security, and an ops bill. That is why a hosted API is often the pragmatic choice even for open models.

In this courseOur code wrapper routes to three providers: Ollama (local, the default), Groq (hosted open, free tier), and Google Gemini (a hosted cloud API, free tier). We reach for a top-end frontier model only where a task genuinely needs it.

ChoosingThe decision rule, said plainly

The habitDefault to the cheapest tier that clears the bar. Move up only when a concrete need (size, speed, or quality) forces you, not by reflex.

MisconceptionNot always the biggest model

"Always use the most capable model" feels safe but is usually incorrect. The largest model is slower, more expensive, and often no better on an easy task.

Classifying a message, extracting a field, or answering an FAQ rarely needs a frontier model. Match the model to the task: a simple, high-volume task does not need the largest model.

ObservabilityFrom print to logging

A stray print is fine for a toy. Real systems use the logging module: leveled, timestamped, and switchable without touching the code. Seed the habit now, because agents (Module 5) are almost impossible to debug without it.

print

One firehose. No timestamps, no severity, no off switch. You comment lines out and back in forever.

logging

Levels let you turn detail up or down: DEBUG (everything), INFO (normal flow), WARNING, ERROR. Set the threshold once; ship at INFO, debug at DEBUG.

Concretely for LLM callsLog the provider, model, token counts, cost, and latency of every call at INFO. When something misbehaves, that record is the difference between a five-minute fix and an afternoon lost.

Front end in 5 minutesStreamlit, just enough

Streamlit turns a Python script into a web app with no HTML. A handful of calls covers today's build; we return to it in the capstone.

import streamlit as st

st.title("Ask the model")
prompt = st.text_input("Your question")      # a text box
if st.button("Send"):                        # a button
    answer = ask_llm(prompt)                 # your wrapper (below)
    st.write(answer)                         # render text on the page
Run itSave as app.py and run streamlit run app.py. The page reruns top to bottom on every interaction, which is the one Streamlit idea to keep in mind.

The buildA three-tier wrapper with a provider switch

One function, one argument, three backends. Flip provider to route the same messages to Ollama, Groq, or Gemini, and log tokens and cost on every call.

  • One chat(messages, provider) entry point.
  • Keys read from a .env file, never hardcoded.
  • Each call logs provider, tokens, cost, and latency at INFO.
  • A tiny Streamlit page in front of it.
