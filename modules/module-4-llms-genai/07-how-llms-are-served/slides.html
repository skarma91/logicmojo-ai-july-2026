The frameWhy it is slow, and what the bill is

A model writes one token at a time, and each new token is a full pass over everything so far. So two numbers decide the experience: latency (how long you wait) and cost (what you pay), both counted in tokens.

As formulasLatency \( \approx T_{\text{prefill}} + N_{\text{out}} \cdot t_{\text{tok}} \) and cost \( \approx N_{\text{in}} \cdot p_{\text{in}} + N_{\text{out}} \cdot p_{\text{out}} \). Here \(N_{\text{in}}\) and \(N_{\text{out}}\) are the input and output token counts, \(T_{\text{prefill}}\) is the time to read the prompt (time to first token), \(t_{\text{tok}}\) is the time per output token, and \(p_{\text{in}}, p_{\text{out}}\) are the per-token prices. Both scale with token counts, which is why tokens are the unit of speed and cost.

Two numbersTime to first token, and throughput

Serving latency splits into two numbers a user actually feels, and different techniques move each one.

Time to first token (TTFT)The wait until the first token appears. It is the prefill cost, reading your whole prompt before anything comes back, and it is what makes a chat feel responsive. Lower TTFT is exactly what Groq's hardware targets.
ThroughputOnce tokens start, how many arrive per second (the decode speed). It sets the total time for a long answer. So total \( \approx \text{TTFT} + N_{\text{out}} / R \), where \(N_{\text{out}}\) is the number of output tokens and \(R\) is throughput in tokens per second. GQA and MQA, quantization, and speculative decoding all push \(R\) up.

The hardwareA mental model of the accelerator

One picture explains most of today. A GPU (or a TPU, or Groq's LPU) is a lot of compute plus two kinds of memory.

Two memoriesHBM (high-bandwidth memory): large, and high bandwidth (much data per second) compared to ordinary computer RAM, but off-chip, so still slower to reach than on-chip memory. SRAM (on-chip static memory): tiny, but very fast, right next to the compute. So "slow" here is relative to SRAM, not absolute: HBM's bandwidth, high as it is, is still the ceiling the model runs into. The GPU's VRAM is this HBM tier (the memory you size a model to fit); SRAM is the small on-chip memory, not VRAM.
Inference is memory-boundGenerating a token does little arithmetic but must move a lot of data, the weights and the growing KV cache, from HBM to the compute. The wait is that movement, not the math. So almost every trick today either moves less data or moves it a shorter distance.

Don't redo workThe KV cache

To write the next token, attention needs the keys and values of every earlier token (class 3.2, Attention). Recomputing them at every step repeats the same work again and again.

The KV cache stores those past keys and values. Each step then computes only the new token and reads the cache, instead of re-reading the whole history. This is the single biggest reason generation is practical.

The cost it createsThe cache grows with the conversation, one slot per token, so a long chat is what fills up GPU memory. Shrinking it is the next two ideas.
Why it is a big winTo produce \(N\) tokens, redoing the key and value work every step sums to \(1 + 2 + \cdots + N = \tfrac{N(N+1)}{2} \approx \tfrac{N^2}{2}\); with the cache each token's keys and values are computed once, about \(N\). That is quadratic redundant work turned into linear (\(N\) is the number of tokens).

Managing the cachePagedAttention: the KV cache in pages

The KV cache grows as a conversation runs, and you do not know its final length in advance. Reserving one big contiguous block per request wastes memory when the answer is short, and leaves gaps too small to reuse when requests come and go.

The ideaPagedAttention stores the KV cache in small fixed-size pages that need not sit next to each other, with a table mapping each request's positions to physical pages, exactly like an operating system's virtual memory. A page is allocated only when it is needed, so there is no over-reservation and no fragmentation.
Why it mattersMore requests fit in the same memory, so batch throughput rises, and a shared prefix can point several requests at the same pages. This is what powers the vLLM serving library.

Don't redo workPrompt caching: reuse the prefix

The KV cache saves work within one answer. Prompt caching saves it across calls. The processed prefix, a long system prompt or a shared document, is stored, so the next call that starts the same way skips re-reading it and pays only for the new part.

Why it mattersA fixed system prompt or a pasted policy is sent on every request. Cached, that shared prefix is processed once, so repeated calls get cheaper and faster. Providers such as Groq, Gemini, and others expose this.
The pricing, made explicitThe saving is on the bill too: frontier APIs charge cached-prefix input tokens at a steep discount, often roughly 10 to 25 percent of the normal input rate. So cost \( \approx N_{\text{new}} \cdot p_{\text{in}} + N_{\text{cached}} \cdot p_{\text{cached}} \), where \(N_{\text{cached}}\) is the reused prefix tokens billed at the lower \(p_{\text{cached}}\) and \(N_{\text{new}}\) is only the new part. A long, stable prefix is where this pays off most.

Cheaper attentionGQA and MQA: share the keys and values

Attention runs several heads in parallel (class 3.3, The Transformer). In standard multi-head attention (MHA) each head keeps its own keys and values, so the KV cache holds a full set per head. Sharing those key and value projections shrinks the cache: multi-query attention (MQA) lets all heads share one set, and grouped-query attention (GQA) shares one set per small group of heads. Smaller cache, faster decoding, for a small quality cost.

The size, as a formulaKV cache \( \approx 2 \cdot L \cdot n_{kv} \cdot d_{\text{head}} \cdot N \cdot b \) bytes: the 2 is keys and values, \(L\) is the number of layers, \(n_{kv}\) the number of key/value sets, \(d_{\text{head}}\) the size of one head, \(N\) the tokens in context, and \(b\) the bytes per number. Only \(n_{kv}\) changes here: MHA uses \(n_{kv} = n_{\text{heads}}\), MQA uses \(n_{kv} = 1\), GQA a few groups. So MQA shrinks the cache by about \(n_{\text{heads}}\times\) (32 heads means roughly 32 times smaller).

Cheaper attentionFlash Attention: the memory bottleneck

Attention (class 3.2) computes a score for every token against every other: \( S = Q K^{\top} \) is an \( N \times N \) matrix, where \(N\) is the sequence length. Standard attention writes that whole matrix to HBM, reads it back to softmax it into \(P\), writes \(P\), then reads \(P\) and \(V\) to form the output \(O = P V\).

Why this is the costThe arithmetic is cheap; the round trips are not. \(S\) and \(P\) are \(N \times N\), so at long context they are huge, and moving them to and from HBM again and again is the bottleneck (memory-bound, from the hardware slide). It also means memory grows like \(N^2\).

Cheaper attentionFlash Attention: tile it, fuse it

Flash Attention never builds the full \(N \times N\) matrix. It splits \(Q\), \(K\), \(V\) into small blocks that fit in fast on-chip SRAM, and for each pair of blocks runs one fused kernel entirely in SRAM.

Inside the fused kernel, per blockScore the block: \( S_{ij} = Q_i K_j^{\top} \). Softmax it to \( P_{ij} \). Accumulate the output: \( O_i \gets O_i + P_{ij} V_j \). All in SRAM; the \(N \times N\) matrices \(S\) and \(P\) are never written to HBM. Only the blocks in and \(O\) out cross, plus two tiny per-row running numbers (next slide).
Same answerThis is exact, not an approximation: identical numbers to standard attention, with far less HBM traffic and no \(N \times N\) memory, so much longer contexts fit.

The key trickOnline softmax: why tiling stays exact

There is a catch. Softmax needs the whole row at once: subtract the row's maximum (for numerical safety), then divide by the sum of exponentials. But tiling only ever sees one block of the row at a time. Online softmax fixes this by carrying two small running numbers per row and correcting as it goes.

The running state, per rowKeep the running max \(m\), the running sum \(l\), and the partial output \(O\). For each new block with scores \(s\):
\( m' = \max(m,\ \max s) \)   (new max)
\( c = e^{\,m - m'} \)   (rescale old work to the new max)
\( l' = c\,l + \sum e^{\,s - m'} \)
\( O' = c\,O + e^{\,s - m'} V_{\text{block}} \)
Finish and why it is exactAfter the last block, divide once: \( O = O / l \). Because every earlier partial sum and output is rescaled by \(c = e^{m-m'}\) whenever the max grows, the final result equals the full-row softmax to the last digit. Nothing is approximated; the row is just accumulated in pieces.
Symbols\(m\): largest score seen so far in the row. \(l\): running sum of exponentials. \(c\): correction factor that re-bases older terms when a bigger score appears. \(s\): the current block's scores.

Fewer bitsQuantization: shrink the weights

A model is millions of numbers (weights). Quantization stores each in fewer bits, 8-bit or 4-bit instead of 16-bit, so the model takes less memory and moves through it faster, for a small accuracy cost.

Why a laptop can run itA 7-billion-parameter model needs about 14 GB at 16-bit but only about 4 GB at 4-bit, small enough for a laptop. This is exactly what lets Ollama serve a capable model locally, and it underlies QLoRA in class 4.10 (Fine-tuning II).
The memory, as a formulamemory \( \approx P \times \tfrac{\text{bits}}{8} \) bytes, where \(P\) is the number of parameters and bits is the bits stored per weight. For \(P = 7\times10^{9}\): \(7\times10^{9} \times \tfrac{16}{8} = 14\) GB at 16-bit, and \(\times \tfrac{4}{8} = 3.5\) GB at 4-bit. Memory is linear in bits per weight, so 16-bit to 4-bit is a 4 times shrink.

Fewer bitsQuantization: the cost, and when to use it

The shrink is not free. Fewer bits means coarser weights, so accuracy drops: a little at 8-bit, more at 4-bit, and most on small models and precision-sensitive tasks (exact arithmetic, code, long chains of reasoning).

Reach for it when

You need to fit a model on a laptop or a smaller, cheaper GPU; serving is memory-bound and a small quality dip is acceptable; you run locally with Ollama; or you fine-tune cheaply with QLoRA (class 4.10, Fine-tuning II).

Be cautious when

The task is quality-critical or precision-sensitive; you already have the memory to run full precision; the model is small (the loss bites harder); or the work is compute-bound rather than memory-bound, so there is less to gain.

Rule of thumbMeasure, do not assume. Quantize, then check your evaluation set (class 4.8, Evaluating LLM and RAG), and ship the smallest precision that still passes.

Draft, then verifySpeculative decoding

Decoding one token at a time is slow because each token is a big-model pass. Speculative decoding puts a small, fast draft model to work: a much smaller model from the same family sharing the same tokenizer (say a 1B drafting for a 70B). It drafts several tokens ahead, and the big model checks all of them in a single pass (it scores every drafted position in parallel), keeping the longest correct run and fixing the first mistake.

Why it is safe and why it is fasterOutput is identical to the big model alone, because the big model verifies every token. The win: one big-model pass confirms several tokens instead of one, and the draft is cheap. The tokenizer must match so the big model can score the exact drafted tokens.
When it pays, as a formulaModel each drafted token as accepted with probability \(\alpha\), for a draft of \(k\) tokens. The expected tokens per verification round is the geometric series \( 1 + \alpha + \alpha^2 + \cdots + \alpha^k = \tfrac{1 - \alpha^{\,k+1}}{1 - \alpha} \): term \(\alpha^i\) is the chance the run survives to depth \(i\), and the leading 1 is the big model's own guaranteed token. At \(\alpha = 1\) this limit is \(k+1\) (every draft accepted, the maximum); as \(\alpha \to 0\) it is about 1 (no gain).

HardwareWhy Groq is so fast

A general GPU is flexible, but it spends time moving weights from its large, slow memory and scheduling work on the fly. Groq's LPU (language processing unit) is built only for inference: it keeps weights in fast on-chip memory (SRAM) and runs a fixed, pre-planned dataflow, so tokens stream out with very low and very predictable latency.

Tie the day togetherKV and prompt caching, GQA and MQA, Flash Attention, quantization, speculative decoding, and the hardware itself are why the same prompt can cost and take wildly different amounts on a laptop, a hosted open model, and a frontier API.

The buildBenchmark the same prompt, two ways

Send one prompt through a 4-bit local model (Ollama) and through Groq, and measure what the day predicted: latency and cost differ, and a repeated prefix gets cheaper the second time.

  • Run the same prompt twice; watch the prefix speed up.
  • Price the tokens at each tier and compare.
