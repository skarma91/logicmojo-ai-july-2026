What is an agent? The loop

RAG answered questions from documents. An agent takes actions: it decides to use a tool, looks at the result, and decides again, until the task is done. Today we build that loop.

The definitionAn agent is four parts working together

A plain LLM answers in one shot. An agent can decide to act, look at what happened, and decide again. Four parts make that possible.

The LLM (the brain)Decides what to do next at each step. It is the reasoning engine, not the whole system.
Tools (things it can do)Functions it can call to affect the world: search a corpus, hit an API, run code. Today's one tool is the Module 4 retriever.
The loop (keep going)Repeat think, act, observe until the task is finished, not a single reply.
Memory (what it carries)What the agent keeps between steps and sessions (built out in class 5.3, Memory for agents).

The defining propertyThe model decides the control flow

In ordinary code, you write the sequence of steps. In an agent, the LLM chooses the next action at runtime, based on what it has seen so far. That single change is the whole idea, and the whole risk.

Why it is powerfulThe path can adapt to each input: search, then decide to search again with a better query, then answer. You did not have to script that branch.
Why it is riskyIf the model drives, the model can loop forever, call the wrong tool, or run up cost. That is why bounding the loop matters from day one (class 5.6).

The lineIf it only produces text in response to text, it is a chatbot. The moment it can decide to take an action and react to the result, it is an agent.

The core loopThink, act, observe

Each turn the agent thinks (reasons about what to do), acts (calls a tool), and observes (reads the result), then loops. It exits when it has the answer.

The analogyA person with a to-do list and a toolbox: do one step, check the outcome, decide the next. Not a fixed recipe, a reaction to what you find.

A detail that is not optionalHow the loop terminates

An agent does not stop on its own. You design the exit. Two conditions end the loop:

Success: a final answerThe model, instead of requesting a tool, signals it is done (in our build, it returns a final answer). That is the normal exit, the loop ends because the task is complete.
Safety: a step capA maximum number of iterations (and later a time or cost budget, class 5.6). The loop runs only while \( \text{steps} \le \text{max\_steps} \) so even if the model never says it is done, the cap stops it. Here steps is how many times the loop has run and max_steps is the ceiling you set.
Why from day oneA loop the model drives can otherwise run forever, so we ship this cap in the very first build, not as an afterthought. It is the first of the reliability rails built out in class 5.6.

What makes it an agentThe agent system prompt

A chat model becomes an agent mostly through its system prompt plus the tool schemas. The prompt states the goal, lists the tools, sets the output contract, and gives the stopping rule. The model fills in the rest.

You are an agent that answers questions using tools when needed. Available tools: search_tax_docs(query): search official tax publications for a fact. On each turn reply with EXACTLY ONE JSON object, either: a tool call: {"tool": "search_tax_docs", "arguments": {"query": "..."}} or a final answer: {"final": "...cite the [id] sources you used"} Call a tool only when you need it; otherwise answer directly.
The pointThe loop and the contract are engineered, not innate. Change this prompt and you change how the agent behaves, which tools it reaches for, and when it stops.

The senior distinctionAgent versus workflow

Workflow
Agent
Control flow
fixed: you write the sequence of calls.
dynamic: the model chooses the next step.
Best for
known, repeatable tasks (extract, then classify, then format).
open-ended tasks where the steps are not known in advance.
Cost and predictability
cheaper, faster, easy to test.
more calls, less predictable, harder to test.
In practiceMost production "agents" are mostly a fixed workflow with a small agentic core where the path genuinely varies. Reach for a workflow first; add agency only where you need it.

RestraintWhen not to use an agent

Do not reach for an agent when
  • The steps are fixed and known: write a workflow.
  • One LLM call, or one call plus RAG, already solves it.
  • You cannot afford unpredictable cost or latency.
  • The task must be exactly reproducible every run.
An agent earns its keep when
  • The path depends on what is found along the way.
  • The task needs several tools chosen at runtime.
  • The number of steps is not known in advance.
  • The work is genuinely open-ended.
The ruleUse the simplest thing that works. An agent is the most powerful and the most expensive and least predictable option, so it is the last one to reach for, not the first.

The gap they fillWhy agents exist

Callback to class 4.6. RAG can answer from documents, but it cannot take actions, call APIs, or run a multi-step task. Agents fill exactly that gap.

A task RAG cannot do"Look up this year's HSA limit, then check whether my planned contribution exceeds it, and if so tell me by how much." RAG retrieves the limit; only an agent can then use it: retrieve, compute, decide, respond.

A modern shift in the workplaceCoding agents: pick one and use it

How software gets written has shifted: most code today is drafted by a coding agent and reviewed by a human. And a coding agent is itself the loop you are learning today, its tools edit files and run commands, so it thinks, acts, observes, and repeats. What the foundations gave you is the judgment to drive one well and to catch what it gets wrong. From here on, use one.

The popular options (pick what you have)Claude Code, OpenAI Codex CLI, GitHub Copilot, Cursor, and opencode. They span free and paid, local and hosted. This course does not mandate one and builds nothing on a specific tool, so choose whichever fits your access and platform.
Review and verifyThe rule from here on: let it draft and scaffold, then read every line before you keep it. You own the code; the agent drafts, you verify.
Misconception"The coding agent wrote it, so I do not need to understand it." Counter: you own every line. Unread generated code is a liability, not a shortcut.

The buildHand-roll the simplest agent loop

One tool (the Module 4 retriever), the think-act-observe loop, and a step cap. The model returns one JSON object per turn (the class 4.3 manual protocol): a tool call, or a final answer.

  • Register the retriever with a name and a description.
  • Loop: model emits JSON, we run any tool, feed the result back.
  • Exit on a final answer, or when the step cap is hit.
  • One demo question needs the tool; one needs no tool at all.
