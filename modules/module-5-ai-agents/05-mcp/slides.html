The problemEvery tool, in every app, by hand

Without a standard, each app integrates each tool its own way. With N apps and M tools, that is N times M bespoke integrations, and every new tool must be rebuilt for every app.

The fixA common protocol turns N times M into N plus M: each app speaks MCP once, each tool speaks MCP once, and they all interoperate.

The ideaMCP is one protocol both sides speak

MCP is a universal plug standard for agent tools. A server exposes capabilities; a client consumes them. Any MCP client can use any MCP server, the way any USB-C charger fits any USB-C device.

Wire onceWrap a database query, an internal API, or the Module 4 retriever as an MCP server once. Every MCP client, now and later, can use it.
A growing ecosystemMany tools already ship MCP servers (files, GitHub, databases, search). Speaking MCP means your agent can use them without custom glue.

A common confusionMCP is not a replacement for an API

An API is one service's own interface: you read its docs and write custom code to call it. MCP is a standard protocol that lets any agent discover and call tools the same way, whatever service sits underneath.

Layers, not rivalsAn MCP server usually wraps an API. MCP standardizes how the agent finds and calls a capability; the API still does the actual work underneath. You do not throw away your REST API, you put an MCP server in front of it (which is exactly what our server does with the Module 4 retriever).
The analogyAn API is the appliance; MCP is the standard wall socket. Each appliance still does its own job. The socket just means one plug fits them all, so the agent does not need a different adapter for every tool.

Misconception"You need Claude or Cursor to use MCP"

MCP is an open protocol, not a feature of one product. Those apps are simply MCP clients you could point at your server. So is your own agent.

Your agent is the clientThe LangGraph agent from class 5.4 becomes an MCP client: it launches your server, discovers its tools, and calls them. No paid app, no cloud account, all local and free. Those apps are optional extra clients, not a requirement.

Under the hoodThe handshake: initialize, discover, call

MCP is JSON-RPC over a transport. The client and server exchange three kinds of message, and "discovery" stops being hand-wavy:

  • initialize: client and server exchange capabilities.
  • list_tools: the client asks what the server offers (discovery).
  • call_tool: the client invokes one by name with arguments.

Two rolesServers expose, clients consume, you build both

The serverWraps your functions as tools and answers the protocol. It does not know or care who the client is. Build it once; reuse it everywhere.
The clientDiscovers and calls the server's tools. Your agent is a client; so are Claude Desktop, Cursor, and others. One server, many possible clients.
Today you build bothA Python MCP server that wraps the retriever and a glossary, and a client (your agent) that discovers and calls them. Seeing both sides makes the protocol concrete.

The server, in codeYour function becomes a tool

With the mcp SDK's FastMCP, a decorator turns a plain function into an MCP tool. Its name, docstring, and typed signature become the schema the client discovers, no separate schema to write.

from mcp.server.fastmcp import FastMCP mcp = FastMCP("tax-tools") @mcp.tool() def tax_glossary(term: str) -> str: """Define a tax term in plain language.""" return LOOKUP.get(term.lower(), "no entry") mcp.run() # serve over stdio
The description carries overThe docstring becomes the tool description, so the same rule from class 5.2 applies: write it for the model, it drives tool choice.

How they connectTransports: stdio and HTTP

stdio (what we use)The server runs as a local subprocess; the client talks to it over standard in and out. Free, local, no ports, perfect for tools that live beside your agent.
HTTP and SSEThe server is a networked service the client reaches over HTTP (streamable HTTP or server-sent events). This is how remote or shared servers work, and where auth becomes necessary.
Same protocol either wayThe messages (initialize, list_tools, call_tool) are identical; only the pipe changes. We build on stdio; the HTTP path is the same code with a different transport.

A real riskAn unknown server is untrusted

MCP tools run real code and their results re-enter the model's context. That makes MCP a security surface, not just a convenience.

The server you connect toA server you did not write is untrusted code running on your machine. Vet it, sandbox it, and give it least privilege, as you would any dependency.
The output it returnsA tool result is untrusted text and can carry injected instructions (class 5.6, Reliability and failure modes). Treat every result as data, never as a command.

Honest scopeWhat we build, and what we name

We buildA custom MCP server exposing tools over stdio, and an agent client that discovers and calls them. Enough to ship a real internal tool.

TransferableThe custom-server skill applies to any internal API or data source: wrap it once as an MCP server and every agent you build can use it.
