The decisionHand-rolled loops get tangled

A `for` loop with a step cap was perfect for learning. But as an agent grows, branches by query type, retries a failed tool, pauses for human approval, persists across turns, the plain loop fills with flags and nested `if`s that are hard to read and test.

A framework gives structureNamed steps, explicit transitions, a state you can inspect, and persistence built in. Behavior becomes a diagram, not a tangle.
Not required from day oneYou built a working agent without one. Reach for a framework when control flow gets complex, not before. Simplicity first.

The modelAn agent is a state machine

Model the agent as a graph over a shared state. Each node does one thing (call the model, run a tool); each edge decides where to go next; the state object carries data between them.

Visible and testableThe agent's behavior is the graph, not logic hidden inside a loop body. You can draw it, test one node in isolation, and reason about every transition.
The same agentNothing about what the agent does changes. Think, act, observe is still the shape; it is now expressed as nodes and edges instead of a while-loop.

Why a graph, not a pipelineCycles are the point

A plain pipeline is a DAG: steps flow one way and stop. An agent needs to loop, act, observe, and decide to act again. LangGraph allows edges that go back, so the think-act-observe loop is a real cycle in the graph, with a conditional edge as the exit.

The differenceA chain runs start to finish once. An agent graph runs the model-tools cycle as many times as the task needs, then routes to the end.

Our graphModel, tools, and a conditional exit

The whole agent, as a graph: enter at the model node; a conditional edge asks "did it request tools?". If yes, go to tools and back to the model; if no, go to END.

Read the flowEvery loop the hand-rolled version did is now one trip around this cycle. The step cap from class 5.1 becomes LangGraph's recursion_limit: pass it at invoke time and the graph stops with a clear error instead of cycling forever.

The dataA typed state every node shares

The state is a typed schema that flows through the graph. Every node reads it and returns a partial update; LangGraph merges each update back in. For our agent the state is just the message list.

class State(TypedDict): messages: Annotated[list, operator.add]
Partial updatesA node does not return the whole state, only what it changed (for example, the new messages). That keeps nodes small and composable.

The gotchaReducers: append, do not overwrite

What a reducer isThe annotation on a state field says HOW updates merge. Default is overwrite: a node's value replaces the old one. operator.add on a list means updates are appended.
The classic bugLeave messages as a plain list (overwrite) and every node replaces the whole history with just its new message. The conversation vanishes each step. The append reducer is what keeps the transcript growing.
The ruleAnything that should accumulate (messages, retrieved docs, tool results) needs an append-style reducer. Anything that should be replaced (a status flag, the latest route) uses the default overwrite.

The wiringNodes, edges, and conditional edges

Three pieces build the graph. Nodes are functions of the state. Edges connect them unconditionally. Conditional edges call a router function that returns the name of the next node based on the state.

g.add_node("model", model_node) g.add_node("tools", tool_node) g.add_edge(START, "model") g.add_conditional_edges("model", should_continue, {"tools": "tools", END: END}) g.add_edge("tools", "model") # the cycle
The routershould_continue looks at the last message: if it holds tool calls, return "tools"; otherwise return END. That one function is the loop's exit condition.

Run itCompile, then invoke

A graph is a blueprint until you compile it into a runnable app, then invoke it with an initial state. Compiling is also where you attach the checkpointer (next slide).

app = g.compile(checkpointer=MemorySaver()) out = app.invoke({"messages": [...]}, config={"configurable": {"thread_id": "t1"}})
Streaming tooBesides invoke (run to the end), a compiled graph can stream node-by-node, so you can watch the agent think and act step by step. Handy for a UI and for debugging.

The payoff featureThe checkpointer: three wins at once

A checkpointer snapshots the state after every node, keyed by a thread_id. That one feature gives three things you built by hand before, for free:

  • Memory: a follow-up on the same thread resumes with prior turns.
  • Resumability: a run that failed can restart from its last checkpoint.
  • Human-in-the-loop: pause at a node, wait for input, resume (class 5.6).

Two questions you are now askingDid the checkpointer replace my memory code?

Two fair questions after the last slide, answered before they trip you up.

Checkpointer vs the class 5.3 storeThey are complementary, not redundant. The checkpointer persists this thread's state (the working memory of one conversation). The class 5.3 MemoryStore holds long-term facts across threads and users, retrieved by similarity. A real agent uses both: the checkpointer for "where were we", the store for "what do I know about this user".
Ephemeral vs durableMemorySaver keeps snapshots in RAM, so they vanish when the process restarts, fine for a demo, not for production. For real deployments use a durable checkpointer (SqliteSaver for a local file, a Postgres saver for a server) so threads survive a restart. Same graph, one line changed.
The rule of thumbCheckpointer = conversation continuity and resumability. Long-term store = durable knowledge. Pick a durable checkpointer the moment the agent leaves your laptop.

The buildRefactor the agent onto LangGraph

Take the class 5.2 agent and rebuild it as a graph: a typed state with an append-messages reducer, a model node and a tool node, one conditional edge that loops until a final answer, and a MemorySaver checkpointer.

What you writeTwo node functions, one router, five lines of wiring, and compile(checkpointer=...). The tools and llm.chat_tools are unchanged from class 5.2.
What you getThe same agent, now inspectable, with persistence: the build runs a query, then a follow-up on the same thread that remembers the first without resending history.
