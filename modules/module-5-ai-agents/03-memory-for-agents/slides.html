Memory for agents

The model forgets everything between calls. An agent that remembers your name, your preferences, and what it just did is not magic, it is memory you design, and manage, on purpose.

The kinds"Memory" is several different things

Lumping it all together is the first mistake. Four kinds, each with a different home and lifetime.

Working memoryThe running conversation and intermediate results in the current context. The notepad on your desk. Lives for this task.
Episodic memoryPast events and conversations, stored and retrieved by similarity. The diary of what happened. Lives across sessions.
Semantic memoryDurable facts and preferences distilled from those events ("files as head of household"). What you have internalized.
Procedural memoryLearned instructions or skills, usually folded into the system prompt. How to do the job.

Short-termWorking memory lives in the context

Working memory is just what you put in the prompt this turn: the recent turns and any intermediate tool results. It is fast and always available, but it is finite and paid for on every call.

The catchKeep the whole conversation verbatim and it grows every turn, raising cost and eventually overflowing the window. Working memory must be bounded, which is what compaction does.

Long-termFacts that outlive the conversation

Long-term memory is a vector store (the class 4.4 store): embed each fact or past turn, and at query time retrieve the few most relevant and inject them into the prompt. This is RAG, pointed at the user's own history instead of a document corpus.

WriteWhen something durable happens (a preference, a decision), embed it and store it, with the dedupe and update policy on the next slides.
ReadEach turn, search the store with the current question and add the top matches as context, so only what is relevant enters the prompt, not everything.

The hard partThe write policy: what to keep, and when

Reading memory is easy. The hard, and most-skipped, part is writing it well. Store too much and retrieval turns noisy and expensive; store too little and the agent forgets.

What to keepDurable facts and stated preferences ("keep answers short", "files as head of household"). Drop transient chatter and one-off details.
When to writeAt the end of a turn, on an explicit "remember this", or when a fact is confirmed. Not every sentence, or the store fills with noise.

Do not pile up copiesUpdate a changed fact, do not duplicate it

If the user's filing status changes, you want one current fact, not two contradictory ones. On write: if a fact with the same key exists, overwrite it; if the new text is a near-duplicate, merge into it. Only genuinely new facts append.

In the buildMemoryStore.add(text, key=...): same key overwrites; cosine similarity above a threshold merges; otherwise it appends.

A sharp warningA wrong memory is worse than no memory

Stored memories go out of date and can contradict each other or the current context. A memory that is retrieved but wrong actively misleads the agent, worse than having nothing, because it answers confidently from a stale fact.

Guard against itPrefer updating over appending (previous slide), timestamp facts where recency matters, and when the current turn conflicts with a stored memory, trust the turn and update the store. Curate on write so reads stay trustworthy.

The pressureA long-running agent fills its own window

Every turn adds history. Left alone, the context grows until cost climbs and the important details get buried or pushed out entirely (the finite window from class 3.5, From models to LLMs).

Two failure modesCost grows with every turn you carry, and quality drops as the signal (the current task) is diluted by pages of old chatter.

The mathWhat each turn actually costs

The tokens you send per turn are the sum of everything in the prompt:

$$ T_{\text{turn}} = T_{\text{system}} + T_{\text{tools}} + T_{\text{memory}} + T_{\text{summary}} + T_{\text{recent}} $$

Reading itT is a token count. system is the fixed prompt, tools the schemas (class 5.2), memory the retrieved long-term facts, summary the compacted history, and recent the verbatim last turns. Cost is roughly \(T_{\text{turn}}\) times the price per token, paid every turn. Only the last two grow with conversation length, so those are what compaction and a buffer window keep in check.

The fixCompaction: summarize the old, keep the recent

Compaction folds the oldest turns into a short running summary, then drops them. The essentials survive in a few tokens while the raw transcript does not keep growing. Recent turns stay verbatim; everything older becomes the summary.

In the buildWhen the buffer passes keep_last, one model call rewrites the summary to fold in the oldest turns, and they are removed. The token count stays bounded.
Compaction is lossyA summary is smaller because it drops detail, so a fact buried in an old turn can be lost. That is why durable facts belong in long-term memory (write them to the store), not left to survive the summary. Keep the summary prompt focused on decisions and preferences so what matters is what it keeps.

Misconception"Just put everything in the prompt"

The tempting shortcut is to keep the entire history and the whole memory store in every prompt. With long context windows it even seems to work at first.

Why it failsCost climbs every turn; latency rises; and quality drops as the key details are buried in noise (models attend worse to the middle of a long context). Memory must be managed, retrieve what is relevant, compact what is old, not dumped. Managed memory is cheaper and more accurate than a giant prompt.

The buildAn agent that remembers across sessions

The class 5.2 agent, given both memories. Working memory bounds the context; long-term memory persists facts and is recalled by similarity each turn.

  • Conversation: a buffer window plus a running summary (compaction).
  • MemoryStore: a vector store with dedupe and update on write.
  • A save_memory tool; relevant memory retrieved every turn.
  • Two sessions share one store: session 2 recalls session 1's preferences.
