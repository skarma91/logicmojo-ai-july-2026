The realityAn agent is not one LLM call

A chatbot answer is one model call. An agent that thinks, calls a tool, reads the result, thinks again, and answers is many calls for a single task, and each call carries a bigger context than the last.

One task, many callsA five-step task is at least five model calls, plus the tool executions between them. Ten steps is not unusual for real work.
The context snowballsEach step re-sends the system prompt, the tool schemas, the memory, and the whole running transcript. The per-call input keeps growing.

Quantify itThe cost of a run

Total cost is the sum, over every step, of what that step's input and output tokens cost:

$$C \;=\; \sum_{i=1}^{n}\bigl(t^{\text{in}}_{i}\,p_{\text{in}} \;+\; t^{\text{out}}_{i}\,p_{\text{out}}\bigr)$$

Every symbol\(n\) is the number of model calls (steps). \(t^{\text{in}}_{i}\) and \(t^{\text{out}}_{i}\) are the input and output tokens on step \(i\). \(p_{\text{in}}\) and \(p_{\text{out}}\) are the price per token in and out.
The trap in the sum\(t^{\text{in}}_{i}\) is not constant: it grows each step as memory and the transcript accumulate (class 5.3). So a ten-step task costs more than ten times step one. Dollar figures here are illustrative.

Why the sum balloonsThe context grows each step

Every step re-sends everything the model needs to see. That pile only gets bigger as the run goes on, which is why late steps cost the most.

The leversA tight tool registry (class 5.2), summary compaction, and retrieving only the memories you need (class 5.3) keep \(t^{\text{in}}_{i}\) from exploding.

Why agents feel slowLatency adds up too

Steps are sequential: each waits on the previous one's output before it can start. So total latency is about the sum of the per-step latencies.

$$L \;\approx\; \sum_{i=1}^{n}\ell_{i}$$

Symbols\(L\) is total wall-clock time, \(\ell_{i}\) is the latency of step \(i\) (the model call plus its tool). \(n\) sequential steps means \(n\) waits in a row.
The leversStream the final answer so it feels fast; run independent tool calls in parallel (class 5.2) to collapse several \(\ell_{i}\) into one; and route easy steps to a faster model.

Lever twoModel routing, with a rubric

Not every step needs your biggest model. Send easy steps to a small or local model, hard steps to a capable one. The saving compounds over a multi-step run.

By step typeA routing decision or a quick extraction goes to a small, cheap model; the final synthesis goes to a strong one.
By capabilityRoute to the smallest model that reliably passes your eval (class 4.8) for that step, not the biggest one available.
By context sizeA step with a large context needs a long-context model; a short step does not pay for one.

Misconception"An agent costs the same as one call"

It does not. A single task can be ten or more model calls, each with a context that grew from the last. Budget for the run, not for one call.

The habitPrint the run's cost and step count every time (the build does this). Once you can see it, caching, routing, a tight registry, and compaction stop being abstract and become the knobs you turn.

IntegrationThe assembled architecture

How the pieces fitIntegration patterns

Retrieval and MCP are just toolsThe model sees one uniform tool registry. Whether a tool is a local function (the retriever) or reached over MCP (the glossary) is invisible to the loop, so you add capabilities without touching it.
Memory wraps the runRead relevant long-term memories into the system prompt at the start; write durable facts back at the end (deduped by key, class 5.3). Working memory lives in the checkpointed state.
Guardrails wrap the loopValidation and the injection scan sit on every tool call; the caps sit on the edges; approval sits before the risky node. The rails are cross-cutting, not one step.
The checkpointer is the spineIt persists the thread (resume later), and it is what makes the human-in-the-loop pause and approve possible (class 5.4 and 5.6).
